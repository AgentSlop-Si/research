# Original-byte identity, privacy and portability

## Preservation boundary

The public directory is the only eligible upload root. Its exact file allowlist excludes the private sibling, compiled executables, bytecode, runtime caches, temporary directories, raw private research-register cells, spreadsheet locators and Library identifiers. Full original reports, code, certificates, manifests and source records remain retained locally. `COPY_BINDINGS.json` exposes their byte lengths and SHA-256 identities, never private local locators.

All reports retain their complete scientific text. Only explicit private path spellings may change. Historical author statuses and review evidence are not silently promoted or rewritten. The top-level release status and final independent review files provide the accepted scope.

## Code adaptations

The original mathematical computations, assertions, inputs, seeds, counters, certificates and test domains are preserved. The only edited executable expressions are input-location expressions listed in `PACKAGING_CHECKS.json` and `COPY_BINDINGS.json`:

- Degree-thirteen `adapt_source.py` reads the three exact predecessor files from the included `adaptation_inputs` directory. This is a source-generation provenance utility; the finished degree-thirteen search and literal-check programs remain unchanged. The three original predecessor programs are provided under their expected filenames.
- The dominant-prime candidate checker reads the included `dependencies/previous_candidate` and `dependencies/previous_review` copies. These are the already-preserved predecessor public packet, including its disclosed private-source omission stubs.
- The dominant-prime reviewer reads the sibling candidate and included predecessor review.
- The sparse-defect reviewer reads the sibling candidate.
- Any centered-family review input-location change is individually disclosed in the byte bindings if required.

The path adaptations are portability changes, not new scientific implementations or rerun evidence. Exact unmodified originals are retained locally. Candidate certificates are byte-identical.

## Private context and source credits

The sparse-defect `REMOTE_INDEX_SLICE.json` and `SELECTED_RECORD.json` copied private research-register cells and spreadsheet URLs. Their public counterparts are expressly labelled omission stubs with the original hashes and a pinned public source-index link. They are not represented as the original source records. The full mathematical Phase20 source, original source credits and all mathematical reports remain present.

Private source-directory fields are removed from source-pin metadata, while repository names, pinned commits, public paths/URLs, byte hashes and source-access qualifications remain intact. Private paths in inert reports, metadata and logs are replaced by release-relative source locations. This changes no mathematical claim.

## Manifests and historical evidence

Original review acceptance binds the exact original candidate files. Public manifests are rebound only where packaging changes a member. Their notices and byte bindings explicitly distinguish public-copy integrity from the original scientific evidence. Historical snapshot manifests, original candidate-manifest copies and recorded hash assertions in results remain historical bindings, even when their corresponding public copy has changed. They must not be interpreted as claims that an original review ran on later public-copy bytes.

The sparse-defect reviewer deliberately checks that its candidate manifest equals the initial review inspection record. Because the public candidate manifest contains disclosed omission stubs, that original inspection hash is expected to differ. For a new scientific reproduction, first make a disposable copy, inspect its candidate manifest and generate a fresh initial inspection receipt there before running that checker. Do not overwrite or relabel the retained original receipt. The mathematical control code itself is unchanged except for its input path.

Run scientific checkers only in disposable copies. Some inherited source files are documentary material rather than standalone executable distributions. The packaging verifier checks only exact allowed paths and bytes. Packaging parses Python syntax without importing or executing candidate or review scientific code.
