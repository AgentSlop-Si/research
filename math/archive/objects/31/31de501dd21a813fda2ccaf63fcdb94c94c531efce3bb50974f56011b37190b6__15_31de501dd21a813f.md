# Research note: packing multiple real FFTs, shared computation DAGs, and tabulated transforms

**Date:** 2026-10-08  
**Status:** Correctness-tested exploratory implementation and analysis. **No claim of a novel sub-`N log N` algorithm for arbitrary complex Fourier transforms.**

## Research question

Can we calculate two different FFTs with one transform plus `O(N)` work and combine that with caching, hash-consing, or a shared computation graph? Can this eventually yield `o(N log N)` or amortized `O(N)`?

### Main results

1. **Yes, for two arbitrary real-valued inputs** `a,b` of length `N`: one complex FFT `Z=FFT(a+i b)`, and `O(N)` arithmetic recovers both `FFT(a)` and `FFT(b)` from Hermitian symmetry. This is a classical technique, *not* a new algorithm. Still `O(N log N)` for the initial FFT.
2. **Yes, for convolution**: with sufficient zero padding, `conv(a,b) = imag(IFFT(FFT(a+i b)^2))/2`. One complex forward FFT and one inverse FFT. This is also known; numeric precision matters.
3. **Yes, for families with low-dimensional structure**: if `M` signals are known linear combinations of `r` basis signals, FFT the `r` bases once and produce all spectra in `O(r N log N + M r N)` arithmetic. If `r=O(1)`, each new spectrum takes `O(N)` after preprocessing; one can detect and verify rank <= 2 in `O(MN)` real-arithmetic work under suitable numeric-conditioning assumptions.
4. **Yes, for sparse edits to a cached input**: if the new input differs in `s` positions, update its spectrum in `O(sN)` arithmetic, after the original FFT.
5. **Exact shared-subproblem FFTs** reduce the number of computed butterflies for repetitive binary inputs; combining packing and hash-consing yields further reductions. For independently random inputs, exact collisions do not establish asymptotic savings beyond constants, and cache overhead can dominate.
6. **Relevant precedent for a genuinely sub-`N log N` lookup speedup:** Josh Alman (SOSA 2023), *Faster Walsh-Hadamard Transform and Matrix Multiplication over Finite Fields using Lookup Tables*, proves `O(N log N / log log N)` **bit operations** over a constant-sized finite field. It does not automatically establish that bound for arbitrary complex FFTs or integer multiplication.

## 1. Two real FFTs using one complex FFT

Let `a,b ∈ R^N`, `A=DFT(a)`, `B=DFT(b)`, `Z=DFT(a + i b)` with forward sign negative. By linearity,

`Z[k] = A[k] + i B[k]`.

For real sequences, `A[(-k) mod N] = conjugate(A[k])` and similarly for `B`. Thus

`conjugate(Z[(-k) mod N]) = A[k] - i B[k]`.

Adding and subtracting gives

```
A[k] = (Z[k] + conj(Z[(-k) % N])) / 2
B[k] = (Z[k] - conj(Z[(-k) % N])) / (2j)
```

There is a subtle but essential distinction:
- This **does not** derive `FFT(b)` from `FFT(a)` without incorporating `b`. Both input arrays are included in the one *complex-valued* transform input.
- The two independent inputs must be real-valued in this construction. For two arbitrary complex inputs, one complex FFT does not carry enough linear degrees of freedom to recover both full transforms; four real scalars per position cannot be injectively encoded into two real scalars per position by a fixed linear map.

## 2. One packed forward FFT for convolution

Let `z = a + i b`; let `*` denote **linear** convolution after padding to `N >= len(a)+len(b)-1`.

```
IFFT(FFT(z)^2) = z*z
                = (a*a - b*b) + 2i(a*b)
```

Therefore

`conv(a,b) = imag(IFFT(FFT(a+i*b)^2))/2`.

This is especially relevant for polynomial convolution underlying ordinary digit-array integer multiplication. For `1234×5678`, use coefficients `a=[4,3,2,1]`, `b=[8,7,6,5]`. The rounded convolution is `[32,52,61,60,34,16,5]`, evaluating at radix 10 gives `7006652`.

Floating-point FFTs are not automatically suitable for arbitrary-size exact integer multiplication without digit splitting, sufficient precision, and rigorous rounding control. Exact NTT/CRT methods offer an alternative.

## 3. Cross-input shared-DAG FFT

Construct the ordinary radix-2 FFT recursion trees for inputs `a` and `b`, but **intern** structurally identical nodes with a shared dictionary. Represent a leaf by `(leaf,value)`, and an internal node by `(size,child_even_id,child_odd_id)`; evaluate each unique node only once.

Define `U_m(a,b)` = number of distinct subproblems of size `m` across *both* trees. The number of radix-2 complex butterfly combinations performed by the DAG is exactly

`B_joint = sum_{m=2,4,...,N} (m/2) * U_m(a,b)`.

To pack, create `z[j]=a[j] + i b[j]`, build a **single** canonical FFT DAG and extract the two real spectra with the identities above. Count only butterfly operations for fair algorithmic comparison; the implementation additionally pays for hashing, construction, allocated spectra, and extraction. In the generic case, storing every distinct intermediate spectrum can require `O(N log N)` memory; this is not a memory-bounded implementation.

### Butterfly counts (correctness cross-checked)

```
N      pair type           two conventional FFTs  joint real-input DAG  one packed-complex DAG
16384  independent bits        229376                 181084                    98664
16384  same input              229376                  91124                    91124
16384  shifted bits           229376                 181068                    91616
16384  two period-8 arrays     229376                  43006                    32764
```

The packed-complex DAG eliminates roughly 57% of butterflies vs the two unshared complex radix-2 FFTs on **this** random binary input. That does not count the inverse FFT or bookkeeping and is **not** a 57% end-to-end runtime saving.

### Pure-Python end-to-end forward-transform timings (milliseconds)

```
N      inputs          two ordinary FFTs     joint DAG       packed DAG + O(N) extraction
16384  random bits         56.606                75.048           46.523
16384  period 8            56.903                27.996           25.329
```

These are exploratory medians of three runs, subject to noise and hardware/runtime particulars. In particular, joint DAG loses on random binary input due to bookkeeping, confirming that butterfly count alone is insufficient.

## 4. Hardware-aware comparison against efficient real FFT routines

NumPy benchmarks of **circular convolution** of two length-`N` arrays (median of 9 runs, milliseconds). Inputs were pre-allocated; time includes transform operations, pointwise math, and inverse, but *excludes* the cost of first preparing the combined input `a + i*b` and FFT planning or repeated external data ingestion. All three methods were checked for agreement.

```
N         FFT(a),FFT(b),IFFT    packed FFT+IFFT     rFFT(a),rFFT(b),irFFT
4096       0.1200                 0.0851               0.0669
16384      0.6200                 0.3705               0.3092
65536      4.8209                 2.6874               1.1215
262144    22.3524                14.1939               6.3118
```

While packing beats **two unoptimized complex FFTs** in this environment, NumPy's specialized **real FFT** implementation is faster. A production benchmark must count all input preprocessing, memory movement and reuse conditions.

## 5. Extending beyond two inputs: low-rank families

Suppose `x_t = sum_{j=1}^r c[t,j] v_j`, where `M` signals share `r` (small) basis vectors `v_j`.

By linearity, `FFT(x_t)=sum_j c[t,j] FFT(v_j)`.

If the representation is known, total arithmetic is `O(r N log N + M r N)` and storage for the `r` basis spectra is `O(rN)`. For constant `r`, an additional signal costs `O(N)` after basis FFTs are cached. If `M >> log N`, the amortized cost per output approaches `O(N)`.

The prototype also discovers and verifies a 2-dimensional real basis from supplied arrays (numerical, not exact symbolic linear algebra). Its search costs `O(MN)` for rank <=2 with fixed rank, but numerical conditioning and false rank decisions must be handled in a production system.

**Measured batch timings: 32 signals, actual two-dimensional span** (ms):

```
N       32 independent batched FFTs    known basis reconstruction    detect + verify + reconstruct
4096           0.658                       0.337                           0.941
16384          5.979                       2.390                           3.742
65536         25.474                      15.049                          19.608
```

This is a genuine use case for combining cross-input caching and graph sharing, but a known/low-dimensional basis is a restrictive structural assumption. Random independent signals generally have growing rank.

## 6. Dynamic relationships also yield linear updates

One changed sample `b[t]=a[t]+delta` gives, for all frequency indices `k`:

`FFT(b)[k] = FFT(a)[k] + delta * exp(-2π i t k/N)`.

One circular shift by `s` gives:

`FFT(roll(a,s))[k] = FFT(a)[k] * exp(-2π i s k/N)`.

Each transformation costs `O(N)` to output all bins once `FFT(a)` is known, and their applicability can be checked in `O(N)` for exact shifts with a Knuth–Morris–Pratt search over the doubled input (implemented in the prototype). For `s` sparse changes, `O(sN)` update arithmetic.

These are already-known Fourier properties; their application to a persistent multi-input transform cache is the engineering direction.

## 7. Why this does not establish `o(N log N)` for arbitrary FFTs

- Two real FFTs in one complex FFT save a **constant number of complete transforms**, not a growing factor as N→∞.
- Collision-only reuse vanishes at large random subproblems because the space of binary input patterns grows exponentially with the block size.
- A bounded-coefficient linear-arithmetic lower bound of Morgenstern (1973) rules out `o(N log N)` in *that restricted model*; it is not a universal lower bound for all computational models including arbitrary lookups.
- The Fourier matrix over complex numbers has twiddle factors depending on N. Directly transferring tabulation results for a **fixed finite-field Kronecker-power** matrix is not immediate. The root-of-unity field/precision size and lookup costs need accounting.
- For linear exact encoding at a fixed input length, two independent arbitrary complex arrays have 4N real degrees of freedom and cannot generally be compressed into a single N-length complex array (2N real coordinates) without loss.

## 8. Closest asymptotic research precedent

Josh Alman, **Faster Walsh-Hadamard Transform and Matrix Multiplication over Finite Fields using Lookup Tables** (SOSA 2023, arXiv:2211.04643), proves

`O(N log N / log log N)` **bit operations** for the Walsh–Hadamard transform over a constant-sized finite field, including precomputation, using lookups to jump across several recursion levels. The paper explicitly constructs a lookup table for all small `H_K * v` instances and applies a Kronecker-power recursion. This is arguably the closest rigorous precedent for the user's *growing N → larger precomputed shared subproblems* intuition.

This is **not** a fixed-power exponent saving `N (log N)^(1-epsilon)`. Dividing by `log log N` gives a smaller savings than dividing by `(log N)^epsilon` for any fixed positive epsilon asymptotically.

Alman and Rao, **Faster Walsh-Hadamard and Discrete Fourier Transforms From Matrix Non-Rigidity** (STOC 2023, arXiv:2211.06459) provide a complementary **constant-factor arithmetic** improvement for ordinary DFTs by circuit redesign. It is relevant to symbolic DAG optimization independently of input collisions.

## 9. Relation to CrocSwap

CrocSwap's historical [shared-computation graph](https://github.com/CrocSwap/integer-mult-bounds/blob/main/docs/research/shared-computation.md) saves *algebraically identical sums* across outputs of a fixed circuit, not merely FFT values for repeated numerical inputs. That makes the circuit-based improvement valid for arbitrary input data, which is essential for its theoretical bound. Newer work also uses recursive batching, compact controls, and specialized data movement.

An interesting research program is to integrate **symbolic** common-subexpression sharing with efficient memory layouts and tight rank/routing certificates. Pure memoization of exact random input values is unlikely to reproduce CrocSwap's asymptotic setting.

## 10. Next milestones

1. Build a dispatcher that estimates costs for `rFFT`, packed-FFT, low-rank basis reconstruction, sparse edit updates, and exact shift detection, accounting for recognition time. Avoid automatically invoking Python hash tables on large random data.
2. Improve DAG memory with an eviction budget, bounded subtree sizes, small-kernel lookup tables, and compact integer signatures. Measure the **full** cost rather than the butterfly count alone.
3. Reproduce Alman's finite-field Walsh–Hadamard table algorithm, including precomputation costs, as a mathematically grounded example of a sub-`N log N` tabulation algorithm.
4. Seek an analogous **proof-compatible** transform family in integer multiplication where small kernels can be tabulated under a fixed alphabet and memory access remains cheap in the target model. Treat this as a research hypothesis, not a proven general FFT algorithm.
