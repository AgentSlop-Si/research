# Fourier graph reuse and projected view corrections

Prepared for 9 October 2026. This phase develops the project's relation-aware
path: reuse computations between known related signals, exploit structure in
their changes, and avoid scanning data that a query does not need.

There are three delivered changes: a version-graph planner, a cyclic-coset
correction representation, and a repair to the newest projected-view replay.
The graph planner improves selected large related batches in local tests.
Small batches and unrelated inputs expose substantial overhead. The underlying
Fourier identities and minimum-spanning-tree algorithm are established tools;
this report makes no research-priority claim for their combination.

## 1. The two graphs have different jobs

The **version graph** has one vertex for each requested signal. An edge is a
known sparse difference between two versions. Traversing an edge computes one
spectrum from another. A virtual source offers a fresh FFT for every vertex.

The **FFT dependency graph** describes how changed coordinates propagate through
a transform. It tells us which subcomputations need work, and when a structured
group of edits can be represented by one smaller transform.

Optimizing either graph alone can miss the cheaper computation. A version far
from the original reference may be one edit from its predecessor. Two equally
sparse differences can also have very different internal transform structure.

The shipped dense interface handles finite real signals and producer-described
real deltas with `1 <= N < 2**31`. Dependency certificates require power-of-two
N; the coset identity works for every positive N in the supported range.
Numerical computations use float64/complex128. Exact finite-field checks verify
the algebra separately, not the floating-point error of every possible run.

## 2. Support geometry gives a weighted coverage function

Let N=2^m and let S be the support of a coalesced input correction. At radix-2
decimation-in-time depth d, active subproblems correspond to occupied residues
modulo 2^d. Put

\[
a_d(S)=|\{p\bmod 2^d:p\in S\}|,
\qquad
W(S)=\sum_{d=0}^{m-1}\frac{N}{2^d}a_d(S).
\]

W counts the scalar output cells at structurally affected internal subproblems
in this particular graph. It is **not** the exact number of nontrivial arithmetic
operations: a node with only one live child can need copies or phase rotations
rather than a full butterfly. It is also not a lower bound on other algorithms.

Since a_d <= min(2^d,k), for k=|S|>0,

\[
W(S)\le N\min\{m,\lceil\log_2k\rceil+2\}.
\]

To see this, the first ceil(log2 k) summands are at most N each. The remaining
summands form a geometric tail bounded by 2N. This recovers the familiar
O(N(1+log(k+1))) zero-pruning bound, but retains the actual geometry rather than
replacing it immediately by k.

At N=262,144 and k=64, the observed exact graph counts are:

| Support | W(S) | W(S)/N |
| --- | ---: | ---: |
| 64 consecutive coordinates | 2,097,024 | 7.99951 |
| 64 evenly spaced coordinates | 524,544 | 2.00098 |
| Seeded random 64 coordinates | 1,918,144 | 7.31714 |

An independent test starts at bit-reversed changed input indices, propagates
influence through the iterative butterfly network, and checks the same counts.

There is also a useful graph-theoretic property. If C_v is the set of input
coordinates feeding an internal subproblem and w_v its output length, then

\[
W(S)=\sum_v w_v\,\mathbf1\{S\cap C_v\ne\varnothing\}.
\]

Each summand is a coverage indicator. Therefore W is monotone and submodular:

\[
W(A)+W(B)\ge W(A\cup B)+W(A\cap B).
\]

The marginal dependency work of another edit decreases as more nearby work is
already active. This explains the benefit of batching edits before propagation.
The test suite checks all pairs of support sets for N=8. Numerical cancellation
can remove further work; this is a structural statement, not a prediction that
every potentially affected scalar has a nonzero numerical change.

This does not prove an optimal greedy cache policy. Cache storage, eviction,
dependencies and runtime costs require a separate objective and proof.

## 3. Compress a whole correction through a cyclic quotient

Suppose every changed position equals r modulo a divisor g of N. Write L=N/g
and delta[r+g*t]=z[t]. Direct substitution into the DFT gives

\[
\widehat{\delta}[q]
=\sum_{t=0}^{L-1}z[t]\omega_N^{(r+gt)q}
=\omega_N^{rq}\widehat z[q\bmod L].
\]

This folds a family of phase-related outputs into L representatives. The
implementation finds the largest admissible g using

\[
g=\gcd\bigl(N,\{p-p_0:p\in S\}\bigr),\quad r=p_0\bmod g.
\]

It reads all k supplied edits, builds a length-L array, and computes its DFT.
The view stores that short spectrum plus (N,g,r). Construction costs
O(k+L log L), numeric spectrum storage is O(L), and a query for Q specified bins
costs O(Q). Materializing the dense real half-spectrum still costs Theta(N).
In an exact arithmetic interpretation, root/phase preparation must be charged;
the numerical implementation generates the needed phases when constructing
outputs. There is no exponential table of possible inputs.

For N=262,144 and positions 3+4096*t, t=0..63, L=64. The correction's numeric
payload is 1,024 bytes versus 2,097,168 bytes for a dense rFFT correction, roughly
a 2,048-fold reduction. The cached base spectrum is additional and unchanged.
The representation is valid for arbitrary amplitudes on those 64 positions.

This is a classical DFT restriction-to-a-coset identity. Its contribution here
is an executable view and its integration into the graph's candidate kernels.
For a random support usually g=1, so no quotient reduction exists. A length-N
complex correction transform plus an addition can then be slower than a fresh
real FFT, as the measured counterexamples show.

The independent modular test checks all 3^8=6,561 vectors with entries in
{-1,0,1}, at N=8 over F_17, against the direct DFT. Floating tests additionally
cover odd lengths, repeated/canceling edits, different residues, full and half
outputs, duplicate selected bins and non-power-of-two divisors.

## 4. A minimum spanning forest chooses reuse parents

Let x_v=x_base+d_v. For each supplied candidate pair (u,v), compute the explicit
coalesced difference d_v-d_u. Give that undirected edge a fixed nonnegative
cost c_uv for its correction kernel. Add a virtual vertex s and edges (s,v)
with cost f_v for fresh computation. An already supplied base spectrum can
instead offer a copy-cost source edge for its unchanged version.

Assumptions for the following claim:

1. Every requested vertex must be computed once.
2. A vertex is computed either freshly or from one already computed parent.
3. Edge costs are symmetric, additive and fixed during planning.
4. Required output arrays are retained and can serve as parent caches.

Every valid one-parent schedule gives a rooted tree on the augmented graph:
each version has one incoming computation edge and every path terminates at s.
Conversely, orient any augmented spanning tree away from s to get a valid
schedule. Thus a minimum spanning tree minimizes the total supplied edge cost
within this model. Removing s gives a forest of reuse components, each with a
fresh/cached root. The implementation uses Kruskal and verifies plans separately
with the maximum-edge-on-path cycle condition. Exhaustive small-graph searches
check the minimum cost without using Kruskal.

Shortest paths are not the same objective: summing root-to-version distances
would charge shared edges repeatedly. The batch schedule pays each selected
computation edge once.

The implementation's weights are measured **runtime estimates**, not exact
runtime costs. It measures copies, a point correction, a quotient lift, and a
native FFT, then extrapolates using k and L. Calibration is charged in cold
benchmarks. Cache effects, signal reconstruction and varying phases can make
these estimates imperfect. Optimal estimated cost does not imply optimal
measured time or minimum cost among all possible algebraic circuits.

### An auditable chain improvement

For versions with 0,1,...,64 distinct cumulative edits, independently applying
each patch to the original reference uses

\[
1+2+\cdots+64=2080
\]

point corrections. Following the chain uses 64. This is a 32.5-fold reduction
in that operation count, **not** a 32.5-fold FFT speedup. A native FFT fallback
is a much stronger baseline than the naive 2,080-correction route. A known chain
also needs no MST: our same-kernel lineage baseline is faster than the general
planner. Graph optimization becomes useful when there are competing parents,
interleaved families or choices between restarting and reusing.

### Charge discovery and memory

If K_v=|d_v| and E candidate version edges are supplied, this implementation
spends O(sum_v K_v) on metadata ingestion and O(sum_(u,v)(K_u+K_v)) on differences,
plus O(E log E) sorting and graph work. It stores the candidate differences.
With all pairs this can become O(M^2 K) metadata work for a common patch-size
bound K. Sparse candidate links make E much smaller; finding those links is
not a free dense-input similarity oracle.

The API retains M real half-spectra, requiring exactly
16*M*(floor(N/2)+1) bytes for those outputs. For 65 outputs at N=262,144 this is
136,315,920 bytes, about 130 MiB, before inputs, metadata and scratch. A streaming
consumer could release outputs, but imposing a small cache budget changes the
planning/scheduling problem; the current MST theorem does not solve that case.

Optional `max_reuse_depth` inserts fresh transforms to limit long numerical
chains. These additional transforms intentionally depart from the MST's cost.
They are a practical drift control, not a formal floating-point error bound.

## 5. Repair the newest projected-view implementation

The uploaded `ProjectedFourierState` correctly chooses replay versus rebuild
using backlog H and current relation size r+k. However its replay loop iterated
over **all E retained events**, skipping previously consumed records. Without
manual compaction, a one-event query therefore incurred O(E+qH) work.

The revised loop takes exactly H entries from the deque's right end and replays
them in chronological order. It preserves the original numerical order and
visits O(H) records. An instrumented-deque regression retains 10,000 consumed
events, adds one new event, and asserts exactly one record visit. A cancellation
test detects accidental reverse-order replay.

With sufficient history, including the returned q-element copy, the bound is

\[
T_{query}=O\bigl(q[1+\min\{H,r+k\}]\bigr).
\]

The +1 matters for a zero-backlog cached query. If history was evicted, the
correct bound is the rebuild cost O(q[1+r+k]), even when H is small. This case
has a dedicated zero-capacity test. History storage also needs O(E) records;
the old numeric storage counter omitted them. The new counter includes 32
numeric bytes per retained version/index/complex-delta record and explicitly
excludes Python/container overhead and the kind tag. `storage_report()` exposes
the components. A bounded log or `compact()` is still needed to bound memory.

This repairs a runtime guarantee; it is not a new Fourier identity. For 300
one-update-plus-query calls with q=8 and 100,000 old records, the original
uncompacted code took about 712 ms, the fixed code 1.07 ms, and the original
with manual compaction 1.22 ms. Old-log construction took approximately 51 ms
for the fixed case and is separately reported. The large speedup is over the
history-scan bug. It is not a speedup over an already compacted implementation
or a full FFT comparison.

## 6. Measurements and their limits

The generated tables in **[RESULTS.md](RESULTS.md)** are drawn directly from
`results/benchmark_graph.json`, `benchmark_history.json` and `memory_results.json`.
There are five outer timing runs per numerical case, with randomized method
order for dense-output comparisons. SciPy's backend is warm, while each method
creates fresh state on every run. Every output bin of every version is checked.

All dense methods retain identical M by (N//2+1) output arrays. Cold graph
timings include initialization, cost calibration, input/edge metadata processing,
MST planning, initial FFTs, correction construction and output writes. The
`fresh_transforms` statistic counts execution only; calibration performs extra
probe FFTs whose time is included in cold totals. Profiled
figures exclude only separately disclosed reusable calibration. The SciPy
competitor directly copies/applies patches and transforms; it does not incur
our graph metadata object's validation costs. Phase 4 and the newly supplied
Phase 5 auto dispatcher are also rerun on the same machine.

Largest local wins include a 65-version chain and interleaved clusters at
N=262,144. Small N=4,096 chains, some medium-sized structured batches and
unrelated patches lose. All-pairs planning is frequently slower than sparse
candidate links. The automatically selected native fallback cannot recover
planning time already spent. Graph use therefore needs to be opt-in or selected
by an application that knows its workload; this release does not claim a
zero-overhead universal dispatcher.

Across the dense benchmark methods the largest observed absolute discrepancy
is about 6.19e-12. This is a finite seeded observation, not a global error bound.
Longer chains, ill-scaled signals and different hardware need their own accuracy
requirements. The separately reported single-correction experiment assumes its
base spectrum already exists; that assumption is not used in the cold batches.

The graph benchmark uses synthetic workloads with declared relationships. No
application-distribution claim follows from them. The isolated memory probe
reports whole-process peak RSS, including the interpreter and libraries.

## 7. Relation to the linked repository and prior work

The GitHub plugin retrieved the linked repository at commit
`741e7aa078392553815df7926ee17ac5e25a8c38`; its README blob was
`09708066640450a0aea89976579b5aba82098ac1`. At that revision it describes a
**conditional** fixed-tape integer-multiplication witness with
kappa=1599247689723/(2.5*10^16), approximately 6.39699e-5. Its README lists
remaining assumptions. This project did not independently verify that theorem
and does not establish that it is the global best result. Its exponent is not
comparable to these floating-point workload timings.

Relevant primary sources:

- [Swapnil Jain, pinned integer-multiplication README](https://github.com/Swapnil-jain/integer-mult-kappa/blob/741e7aa078392553815df7926ee17ac5e25a8c38/README.md).
- [Reif and Tate, On Dynamic Algorithms for Algebraic Problems](https://scholars.duke.edu/publication/754154): prior dynamic Fourier work; dynamic updates are not a newly introduced problem.
- [Tapia et al., eFFT implementation and publication references](https://github.com/raultapia/efft): maintains an FFT tree and reuses event/packet computations. This package contains no eFFT implementation and makes no speed claim against it.
- [FFTW, pruned FFT notes](https://fftw.org/pruned.html): pruning is established and smaller arithmetic counts can lose to optimized full transforms.
- [Frigo, A Fast Fourier Transform Compiler](https://www.fftw.org/pldi99.pdf): FFT computation DAGs and common-subexpression optimizations predate this project.
- [Guo et al., To Store or Not to Store](https://arxiv.org/abs/2402.11741): graph-based version/delta storage and reconstruction have substantial prior literature. Our additive one-parent model is narrower than its storage/retrieval tradeoffs.

These references place the tools in context. They do not establish priority for
this implementation or prove its machine-dependent benchmark numbers.

## 8. What this establishes and what to test next

The delivered evidence supports selective reuse across a supplied version graph,
support-aware compressed correction views, and a corrected event-history cost.
It does not derive a new bound for fresh arbitrary full DFTs or arbitrary exact
integer multiplication. In particular, general independent FFT subtrees are not
made identical by storing them in a graph.

The most useful next experiment is an actual producer with branching versions
and a consumer that can retain projected or quotient views. Measure whether it
can provide a sparse candidate graph cheaply and avoid dense intermediate
outputs. Compare the simple producer lineage before invoking global planning.
Only after that should a memory-constrained DAG/cache scheduler be attempted.
Any claimed asymptotic improvement must include relation discovery, graph
construction, precision, cache storage and requested output volume.
