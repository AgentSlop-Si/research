# Phase 9 research audit: Compiled polynomial jets for persistent convolution

**Date:** 2026-10-09. **Status:** working numerical code, checked against independent SciPy and exact modular arithmetic. **Not a new sub-`N log N` algorithm for arbitrary fresh DFTs, and not a new integer-multiplication upper bound.**

## Question and contribution

Can we close Phase 8's gap to a hand-written *single-edit* convolution update by compiling its symbolic polynomial-jet expression into one fused native loop, rather than interpreting a shared graph and materializing a separate shifted NumPy array for each correction kernel?

**Answer from this project:** yes, for the measured fixed-degree streams, while charging for cold compilation. In a controlled 12-round repeated benchmark at N=262144, degree 3 and 48 full-output variants, the generated native code took **17.74 ms median**, compared with **18.97 ms** for a hand-written native update and **18.43 ms** for the Phase-8 NumPy version. That is a machine-specific result; reruns varied and occasionally reversed the ordering. True fresh-process cold timings were **600.70 ms** for the generated implementation versus **58.21 ms** for Phase 8 and **314.13 ms** for prepared-kernel SciPy recomputation at the same size and workload. These measurements show JIT compilation is only attractive after enough reuse (or code caching) to amortize its fixed cost.

We do **not** claim that compiled kernels always beat hand-written formulas, SciPy on every problem size, eFFT, or OpenAI's exact Fourier circuits.

## Mathematical identity and proof

Work in the length-N circular-convolution ring `R = K[z]/(z^N - 1)` over a commutative coefficient ring K. Let `F(x, other variables)` be a finite polynomial expression built using addition, convolution and fixed scalar multiplication. Fix all leaves except x. By polynomial arithmetic there are unique coefficient elements `K_h in R` such that

`F(x+u) = sum_{h=0}^d K_h * u^{*h}`,

where `u^{*0}` is the convolution identity, a unit impulse at 0. These are Hasse/Taylor coefficients and do not require division by `h!`. For one known input edit `u = δ e_t`:

`u^{*h} = δ^h e_{(h t) mod N}`.

Convolution by an impulse shifts the sequence, so every output coefficient is

`F(x+δe_t)[q] = K_0[q] + sum_{h=1}^d δ^h K_h[(q-h t) mod N].`

That equation is exact over K. If some K_h is an explicitly known sum of impulses `sum_s c_s e_s`, the corresponding update adds `δ^h c_s` only to position `(s+h t) mod N`, with no dense scan for that term.

### Generated fused evaluation

The generator retrieves the Phase-8 `PreparedEdit` coefficient kernels and the **symbolic** sparse-impulse certificates; it does not infer exact zeros from floating point. It constructs a straight-line body with **one** pass over output locations:

```
shift_h = (h * position) mod N
scale_h = delta ** h
for q in 0..N-1:
    out[q] = K0[q] + sum_dense scale_h * K_h[(q-shift_h) mod N]
for (h,s,c) in sparse terms:
    out[(s+h*position) mod N] += (delta ** h) * c
```

The actual output Python source unrolls known dense degree terms and sparse edits. Numba compiles this fixed, numeric form to machine code. It allocates the result exactly once, does not call a Python graph visitor per output, and does not create a temporary rolled array per coefficient.

The algorithm is **O(N d_dense + s)** per full N-element output after preparation and JIT, where `d_dense <= d` and `s` is the total number of nonzero symbolically sparse correction impulses. It takes `O(Q(d_dense+s))` work for Q selected coefficients with a simple loop, before dispatch overhead. For fixed degree and bounded sparse correction size, producing a full dense result is `Theta(N)` and therefore asymptotically output-optimal for the *restricted cached update problem*.

The prior Phase-8 jet preparation remains necessary. A conservative precomputation bound from its implementation is initial seed FFT work `O(SN log N)` plus coefficient propagation `O(E d² N)` and up to `d+1` inverse FFTs `O(d N log N)`, plus symbolic construction, materialization and JIT. The generated execution representation uses `O((d_dense+1)N+s)` extra real-number storage when stored densely. **The JIT compilation complexity is treated as a separately measured, fixed-for-shape cost, not magically free.** This is not a uniform bit-complexity proof for arbitrary d, graphs or machine models.

### Concrete repeated-input example

`F(A) = A*A*A + 2 A*B + C*D`.

The coefficients of `F(A+u)` are:

```
K0 = A*A*A + 2A*B + C*D
K1 = 3A*A + 2B
K2 = 3A
K3 = e0
```

Hence

`F(A+δe_t)[q] = K0[q] + δ K1[q−t] + δ²(3A[q−2t]) + δ³ [q=3t mod N]`,

with indices wrapped modulo N. The compiler automatically produces that data-flow, including the final sparse correction.

## Verified implementation details

- `compiled_kernels.py` builds deterministic shape-bounded generated code: max degree 8 by default, hard limit 16 and bounded sparse term count; every interpolated identifier is an integer from validated graph metadata, not user-supplied Python source.
- The compiler supports odd and even N, arbitrary positions, positive/negative real edits, repeated frequency queries, and zero-degree graphs.
- `numba` execution is optional. `backend='python'` executes exactly the same generated source without native JIT. The separate `auto_dispatch.py` guards against first-use JIT cost, samples both prepared and compiled kernels on the same inputs, and chooses whether projected reuse amortizes the measured startup. It does not prove that its heuristic is globally optimal.
- A generated source string is available for review through `compiled.generated_source`.
- The Phase-8 engine stores input real transforms with SciPy rFFT. There is no code implementing OpenAI #130's exact arithmetic circuit or the CrocSwap integer-multiplication machine.

## Correctness

The packaged Python regression suite (original Phase-8 plus Phase-9 tests) has 23 passing test cases; the new Phase-9 exact-integer comparison performs 120 independently generated modular-convolution trials over primes 17, 97 and 257, with small enough magnitudes for exact integer results in the double-precision execution. The legacy Phase-8 `exact_modular_audit.py` passes 480 independent cases over F97. New tests cover 0–4 polynomial degrees and odd lengths, full outputs, partial outputs, strict memory limits, invalid indices and source generation limits.

Every full-size performance workload is also validated against an independent SciPy convolution on multiple entire N-element arrays before timings are accepted. Maximum tested absolute difference at N=262144 was below `2e-17` for the generated FFT correction route in the three benchmark expressions. This is numerical agreement, not a worst-case floating-point error guarantee.

| N, degree | SciPy | Phase 8 | Phase 9 generated | Hand Numba |

The large JIT penalty is real. Merely comparing a warmed compiled kernel with a cold SciPy FFT is not fair. Generated source/signature reuse across different N in one process can amortize that cost over future sessions; `isolated_cold.py` and `run_isolated_cold.py` intentionally suppress that hidden benefit by starting fresh interpreters.

### Selected output coefficients

For six selected coefficients per edit (48 cubic edits), the warm generated approach took approximately 0.45–0.55 milliseconds per 48 queries in the recorded runs; hand-crafted six-bin math took a similar amount. Neither method computes the full N samples. It is inappropriate to report this as a full-FFT acceleration.

## Comparison with relevant prior art

- Fast Fourier transforms and the convolution theorem are classical.
- Taylor/Hasse coefficient propagation, automatic differentiation and polynomial jets are established; see `jax.experimental.jet` and earlier arithmetic-circuit differentiation.
- Event-based FFTs are established; [eFFT](https://github.com/raultapia/efft) (Tapia et al., IEEE TPAMI 2024; eFFT-C++ release in Journal of Open Research Software 2026) maintains a radix-2 transform tree for asynchronous event streams. It is not an equivalent sum-product convolution evaluation task. `COMPARE_EFFT.md` records this boundary.
- OpenAI result #130 concerns fresh exact DFT/convolution in an unrestricted complex-field arithmetic model, not this bounded-degree cached edit execution. CrocSwap aims at integer multiplication bit complexity in a specified multitape model. Neither complexity result follows from our benchmark.

**What we gained:** the automatic dynamic formula execution now reaches performance comparable to a specialized hand-written native implementation for the tested repeated-update workloads. This is a useful engineering milestone, not a universal algorithmic-complexity breakthrough.

## Next falsifiable steps

1. Move first-use compilation to prebuilt/AOT machine code and measure end-to-end fresh-process total time; keep native cache and dependency provisioning costs explicit.
2. Generate small multivariate update jets (two simultaneously edited leaves), using sparse symbolic supports to avoid O(d1*d2) dense coefficient blow-up.
3. Optimize memory traffic (single fused pass, multithreading, prefetch) with hardware counters and controlled core affinity; add size-specific crossover calibration.
4. Compare identical event-stream FFT workloads with an actual eFFT installation, respecting its 2D event semantics and required output scope rather than comparing unrelated tasks.
