# Consumer-aware lazy relation FFT — research checkpoint

**Date:** 2026-10-09

## Status

This extends the relation-aware adaptive FFT project with deferred spectrum
materialization, selective frequency views, and threshold compaction.

It is **not** a new worst-case FFT theorem. Dynamic/incremental DFT is old
(Reif–Tate, 1997, among others). The contribution here is a reproducible
engineering architecture and workload model that directly addresses the
bottleneck found in the previous audit: relation discovery, dense output writes,
and memory traffic can dominate even after moving bookkeeping to C++.

All current regression tests pass: **22 tests**.

## 1. Representation

Maintain a spectrum in the symbolic form

\[
S = \sum_{i=1}^{r} \alpha_i B_i + F_N(e),
\]

where the `B_i` are already-computed dense cached spectra and `e` is a sparse
set of producer-supplied time-domain edits.

The new `LazySpectrum` does not touch all `N` bins when metadata arrives.
Duplicate point edits are aggregated by location.

For `k` distinct pending edit locations:

- metadata point update: expected `O(1)` dictionary work;
- `q` requested Fourier bins: `O(q(r+k))` arithmetic;
- explicit dense materialization: `O(rN)` plus the selected sparse-correction
  backend (`direct`, grouped/factorized, or native FFT fallback).

This makes the **consumer's requested output size** part of the planner. Dense
output still costs at least `Omega(N)` just to emit.

## 2. Fixed support + fixed bins: PreparedBinView

If the producer knows that edits can only occur in a fixed support `K` of size
`k`, and the downstream consumer repeatedly asks for a fixed set `Q` of `q`
frequency bins, precompute only

\[
P_{u,j}=\exp(-2\pi i u j/N),\qquad u\in Q,\;j\in K.
\]

Then:

- preparation: `O(qk)` arithmetic and memory;
- update one allowed time-domain position: `O(1)`;
- return all `q` selected bins: matrix-vector work `O(qk)`;
- phase-cache memory: `Theta(qk)`, versus `Theta(Nk)` for storing a full
  N-bin phase vector for every editable position.

The exact memory reduction is therefore

\[
\frac{Nk}{qk}=\frac{N}{q}.
\]

### Median benchmark, 3 runs

`N=262144`, 500 updates, fixed support of 32 locations, 64 requested bins:

| Method | Total time |
|---|---:|
| Fresh FFT after every update | 2882.04 ms |
| Full N-bin phase bank + eager dense spectrum update | 759.05 ms |
| **PreparedBinView** | **7.49 ms** |

Observed speedup: **384.6x vs fresh FFT**, **101.3x vs eager dense phase
updates**.

Prepared phase memory was **32 KiB**, compared with **128 MiB** for 32 full
complex phase vectors: exactly **4096x less memory**, equal to `N/q`.

These are hardware-specific numerical measurements, not asymptotic theorem
claims.

## 3. Low-rank + sparse selected-bin views

A relation state

\[
x = \sum_{i=1}^{r} c_i b_i + e
\]

with cached `F(b_i)` does not need an `N`-length reconstruction if only `q`
frequency bins are consumed. The query is

\[
F(x)[Q] = \sum_i c_iF(b_i)[Q] + \sum_{j\in\operatorname{supp}(e)}
 e_j\,\omega_N^{Qj}.
\]

Cost: `O(q(r+k))`, versus eager dense reconstruction `O(Nr + Nk)` for a
simple direct implementation.

Median benchmark at `N=262144`, `r=4`, `k=64`, `q=64`:

- eager dense relation reconstruction: **1243.86 ms**;
- lazy selected-bin view: **3.09 ms**;
- observed ratio: **402.6x**.

The point is not the exact ratio; it is that partial consumers should not force
full-spectrum materialization.

## 4. Lazy forever is not optimal: threshold compaction

When edit locations keep accumulating, selected-bin queries eventually cost
`O(qk)`. `BufferedSpectrum` therefore compacts pending edits after a threshold
`B`: it materializes one correction and folds it into the dense cached base.

For a workload with roughly distinct updates, one q-bin query every `H`
updates, and a dense flush cost `C(N,B)`, a simple steady-state proxy is

\[
\text{cost/update}\approx \frac{C(N,B)}{B}+\frac{qB}{2H}.
\]

If `C` is approximately independent of `B` over the relevant range (a good
first model for a native full FFT fallback), the optimum is

\[
B^*\approx\sqrt{\frac{2CH}{q}}.
\]

This predicts the qualitative behavior seen in the benchmark: when queries are
frequent, moderate compaction wins; when queries are rare, the best policy is to
keep edits lazy for much longer or never flush during the observed horizon.

### Median benchmark, 3 runs

`N=262144`, 512 distinct point edits, 64 requested bins every 4 updates:

| Policy | Time |
|---|---:|
| Fresh FFT on each query | 776.19 ms |
| Never compact pending edits | 139.01 ms |
| **Compact every 128 distinct edits** | **83.91 ms** |

The thresholded policy was **9.25x faster than fresh FFT queries** and **1.66x
faster than never flushing**. It performed four dense correction flushes.

A broader one-shot sweep showed the best threshold moving upward as queries
became rarer, approximately following the square-root tradeoff. For some
rare-query workloads, no compaction within the 512-update horizon was best.

## 5. Dense flush reality check

The grouped sparse decomposition remains mathematically useful and is the right
place to plug in a future exact #130 backend. But on the present SciPy runtime,
constructing a sparse N-vector and calling the highly optimized native FFT is
often faster than the Python factorized prototype for dense output.

This is why `LazySpectrum.materialize` now exposes three explicit choices:

- `direct`: phase accumulation, good only for tiny `k`;
- `factorized`: the parameterized sparse decomposition, useful for algebra and
  a future exact fast small-DFT backend;
- `native`: construct the sparse correction vector and use the optimized FFT.

The runtime planner should therefore distinguish **asymptotic backend cost**
from **current numerical wall-clock cost**.

## 7. What is actually new here?

Do **not** claim a new dynamic-DFT asymptotic theorem. Reif and Tate already
studied online input changes/output queries and gave an `O(sqrt(N))` per-request
incremental DFT algorithm in 1997.

The defensible project contribution is the **consumer-aware relation runtime**:

1. upstream relation metadata instead of O(N) relation discovery;
2. deferred symbolic spectrum state instead of eager N-bin writes;
3. selective phase caching proportional to requested output (`qk`, not `Nk`);
4. low-rank + sparse partial views;
5. explicit dense-output boundary;
6. threshold compaction with an analyzable workload tradeoff;
7. a practical planner that can choose a native FFT even when a theoretically
   prettier sparse decomposition is slower on real hardware.

This is the path that remains genuinely distinct from the CrocSwap / integer
multiplication circuit-constant race.

## 8. Next research target

The highest-value next step is to make the threshold planner **self-calibrating
and persistent** across `(N, q, query-rate)` regimes, then port only the
`PreparedBinView` and buffered compaction hot loops to C++/SIMD. The earlier C++
experiment showed that removing Python alone is insufficient when memory scans
remain; this design avoids those N-wide scans on partial queries by construction.

A second target is a prepared relation view where both low-rank coefficients and
point edits change online. That would store only `q*r` basis-bin values and
`q*k` phases for a fixed consumer view, while allowing O(1) coefficient/edit
metadata changes and O(q(r+k)) reads.
