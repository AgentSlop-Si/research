# Independent review of the exact correction graph

**Verdict:** the reviewed implementation correctly realizes exact finite
same-B integer-product reuse under its declared assumptions. The graph
optimality claim is restricted to its supplied candidate edges and fixed
scalar-arithmetic kernel weights. It establishes neither arbitrary-input
sub-N-log-N multiplication nor a wall-clock improvement.

Reviewed files: `correction_graph.py`, `audit.py`, and
`audit_numeric_shifts.py`. Final implementation hashes are recorded in
`independent_review_checks.json`. The independent checks are deliberately
targeted at modular boundaries, carries, cache identity, and duplicates;
they do not repeat the author's complete audit.

The final README's correction invariant, restricted MST theorem, cold/warm
ledger, logical-counter qualifications, and sparse-discovery/planner distinction
were also checked for consistency with the implementation.

## Exact arithmetic and carries

For canonical length-n base-b digits, every ordinary convolution coefficient
lies in [0,n(b-1)^2]. The implementation requires this upper bound to be
strictly below p=65537 and the padded power-of-two transform length to divide
p-1. Thus the inverse NTT's canonical residues are the actual integer
coefficients, not merely congruent substitutes. For base 16 the supported
digit-bound limit is n=291. With base at least two, the transform-length
limit additionally requires n<=32768; a larger radix can impose a much
smaller limit. This fixed backend supplies no unbounded-size asymptotic
integer-multiplication implementation.

In default mode a patch is the exact coefficientwise difference between
two input digit polynomials. Adding patch*B to the parent's raw convolution
therefore yields the child's raw convolution. Signed corrections are computed
in ordinary integers, not wrapped modulo p.

In numeric-patch mode the cached product is a canonical 2n-digit vector.
The patch may instead contain the signed canonical digits of the actual
integer difference. Polynomial equality then need not hold; equality after
evaluation at the base is the correct invariant. Both available patch
representations satisfy that invariant. Adding their product with B to the
cached canonical product and carrying again yields the exact target integer.
Python's floor `divmod` handles negative intermediate carries correctly.
Since each final product lies in [0,b^(2n)), the final carry is zero.

Independent controls pass at the tight coefficient boundary 65536
(n=1,base257), at n=291/base16, and for positive/negative corrections.
Out-of-range cases are rejected. Numeric-mode controls around
base^(n-1)+{-16,-2,-1,0,1,2,16} pass for n=3 and n=64, including long carry
chains and warm reuse.

## MST scope and charged work

The planner is Prim's algorithm on a virtual source plus the query vertices.
A source edge selects a fresh product; a query edge selects one verified
correction. Weights are symmetric and nonnegative. A warm anchor receives
a zero-weight source edge. The cut argument therefore proves minimum total
edge weight for this fixed graph. For a supplied sparse graph the optimum
is only over those supplied edges. More general multi-parent formulas,
different correction kernels, and bit- or memory-weighted objectives are
outside this claim.

The fresh kernel's arithmetic weight matches two NTTs, pointwise multiplication,
and inverse scaling. A nonempty support-s correction costs 2ns integer
operations plus the product-vector merge. An empty patch costs no scalar
arithmetic but still copies its parent's vector. Every returned product
also incurs a full 2n-digit carrying/output pass. The duplicate control
confirms one fresh product, two explicit vector copies, and all 18 output
digits for three length-three inputs.

Cold scalar totals include root preparation, the transform of B, discovery,
product kernels, and all normalization arithmetic. Warm timings/counts must
be interpreted with the previously paid seed explicitly restored. Raw-cache
seed construction and canonical-cache seed construction differ by an initial
normalization pass; the author's numeric audit explicitly accounts for it
and for rematerializing the anchor output.

Metadata counters are selected logical categories, not an exhaustive count
of Python instructions or every allocation/load/store. For example some
list and slice copies are covered by the stated linear work rather than a
dedicated exact counter. Arithmetic-count savings alone should therefore not
be labeled total-machine-work or wall-clock savings.

For Q queries, full pair discovery costs O(Q^2 n). With E supplied distinct
candidate edges, verified difference discovery costs O(En), plus reading and
deduplicating the supplied edge records. The current planner still scans
all Q vertices each round and costs O(Q^2), even when E is small. Outputs
require O(Qn) work. Stored patches require O(En) worst-case records in sparse
mode, or O(Q^2 n) for the complete graph. These costs remain part of the
end-to-end algorithm.

Independent candidate-graph controls pass: an empty graph uses seven fresh
roots; two disconnected candidate edges use five; a connecting chain with
reversed/duplicate edge records uses one. All outputs remain exact.

## Cache trust boundary and review fixes

The warm-key checks reject mismatches of A, B, base, length, query index,
and raw-versus-canonical representation length. Review identified missing
integer-base and valid-index guards; those are now present and tested.

The context and product coefficients must come from trusted internal
computation. Matching A/B keys does not authenticate arbitrary supplied
coefficients or a mutated context. An independent negative control deliberately
changes a cached coefficient: the API accepts the matching keys and returns
the correspondingly incorrect result, as expected for this trusted-cache
interface. This limitation is explicit rather than presented as cache-content
verification.

All targeted checks pass. No unresolved mathematical correctness issue was
found within these assumptions and the supported finite range.
