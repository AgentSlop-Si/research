# C++ adaptive FFT bookkeeping experiment — findings

Date: 2026-10-09

## Question

Is Python bookkeeping (hashing, dictionaries, graph/cache management) the main reason structural FFT reuse loses to optimized FFTs?

## Setup

The hot path was ported to C++20 and benchmarked against the same FFTW real-to-complex backend used by the adaptive path. The port includes exact-input caching, full-byte verification, sampled sparse-change screening, exact sparse verification, cyclic-shift detection with KMP over IEEE-754 bit patterns, phase reconstruction, rank<=2 detection, and known-basis reconstruction.

The benchmark is an ablation study:

- `hash_only`: fingerprint then always FFT.
- `exact_cache`: fingerprint + exact cache.
- `structural`: exact cache + shift/sparse detection.
- `rank2_detect`: detect rank<=2, perform only basis FFTs, reconstruct outputs.
- `known_basis`: basis and coefficients supplied directly.

All numbers are local exploratory wall-clock medians, not universal performance claims.

## Strongest observations

### 1. Exact repeated transforms benefit in compiled code at large N

For 12 repeated transforms:

| N | structural speedup vs FFTW baseline |
|---:|---:|
| 65,536 | 1.76x |
| 262,144 | 1.89x |

This validates that caching can beat recomputation once the FFT is large enough, even while hashing and full verification are counted.

### 2. Python is not the only bottleneck for shift reuse

At N=65,536, shift reuse was only 0.38x baseline; at N=262,144 it was 0.56x. C++ removed interpreter/object overhead, but exact shift detection still scans memory and reconstruction still writes O(N) complex output. Those costs are large relative to FFTW.

At N=262,144 (12 shifted transforms), representative component timing was approximately:

- relation detection: 31.60 ms
- reconstruction: 10.10 ms
- FFT work (seed): 2.34 ms

So the dominant cost is now the relationship-search/reconstruction path itself.

### 3. Sparse update reuse approaches break-even at larger N

For one changed sample per signal:

| N | structural speedup |
|---:|---:|
| 65,536 | 0.60x |
| 262,144 | 1.00x |

This is much more promising than shifts. The next optimization should make sparse deltas available upstream instead of discovering them by scanning the whole vector. If the producer tells the engine `(index, delta)`, relation detection collapses from O(N) scanning to O(1) metadata and only O(N) spectrum update remains.

### 4. Unrelated inputs remain a loss when aggressive structural search is forced

At N=262,144, structural mode was ~0.45x the plain FFTW baseline on unrelated inputs. This supports the original Python engine's conservative `auto` policy: do not aggressively scan for structure when recent inputs look high-entropy/unrelated.

### 5. Low-rank reuse is computationally real, but output materialization matters

With M=128 and rank=2, only two basis FFTs are needed. However this C++ prototype explicitly materializes all M spectra with a simple C++ reconstruction loop. At N=65,536, known-basis mode was ~1.02x baseline rather than a huge win.

This does **not** invalidate the low-rank arithmetic saving. It shows the next bottleneck: writing M x (N/2+1) complex outputs and performing the linear combinations can become comparable with highly optimized FFTW. A compressed API that keeps results as `(coefficients, basis_spectra)` until consumers actually request dense spectra could avoid this output-materialization cost.

## Interpretation

The experiment rejects the simple hypothesis “Python bookkeeping is the main problem.” It is a problem, but after moving bookkeeping into C++, three more fundamental costs remain:

1. reading O(N) input to discover a relation;
2. writing O(N) spectrum for every requested dense result;
3. memory bandwidth/cache traffic from storing full inputs and spectra.

That points toward a stronger architecture:

`producer metadata -> certified relation -> basis-spectrum representation -> lazy materialization`

Rather than:

`dense input -> scan/hash/search -> discover relation -> materialize dense spectrum`

The former can skip much of the work that currently consumes the theoretical gain.

## Next experiments

1. Add a **trusted sparse-delta API**: `fft_from_delta(base_id, index, delta)` and benchmark without O(N) relation discovery.
2. Add a **trusted shift API**: `fft_from_shift(base_id, shift)` so shift detection is O(1).
3. Add a **lazy low-rank spectrum object** storing coefficients + 1–2 basis spectra without materializing M dense FFT outputs.
4. Replace full-input fingerprints with chunk hashes / tree hashes when the producer can update them incrementally.
5. Benchmark hardware counters (cache misses, memory bandwidth, branch misses) and pin the benchmark to one CPU core for tighter variance.

These tests are more likely to expose a genuine amortized advantage than simply making the current scanner faster.
