# Compiled binary-input FFT leaf-table experiment

This is a standalone, single-threaded C prototype with benchmarks and a reusable
adaptive API, not a production FFT library or a modification of the original
FFT implementation.

For the ready-to-use API, start with **ADAPTIVE_README.md**. It leads with an
explicit zero-calibration arithmetic path for one-off calls, then explains the
cached adaptive selector for heavily repeated transforms.

## Reproduce

Requirements: GCC, Python 3, NumPy, SciPy. No downloaded dependencies are used by
the harness. From this directory run:

```sh
python benchmark.py --output results.json
```

The harness compiles `leaf_fft.c` relative to its own location. A quick correctness
and timing smoke test is available with `python benchmark.py --quick`.
The longer C-only confirmation run used:

```sh
python benchmark.py --rounds 21 --target-ms 100 --skip-practical --output results_confirmation.json
```

Results are specific to the recorded virtualized CPU, compiler, array sizes, and
input representation. Re-run on the intended machine before choosing a cutoff.
Do not load a generated shared library from an untrusted source; build locally.

## Fairness controls

- Every method takes the same binary `uint8` input and writes all N outputs as
  `complex128`. Inputs must contain only 0 or 1, and N must be a power of two.
- The ordinary baseline is already iterative: no Python, recursive calls,
  dictionary lookups, tuple creation, or hash cost. It fuses bit-reversed input
  gathering with arithmetic two-point leaves and has a specialized four-point
  merge stage.
- Arithmetic codelets of lengths 4, 8, and 16 provide stronger controls. They fuse
  the same input gathers with real-input arithmetic and use no spectrum cache.
- All methods use the identical radix-2 merging routine after their leaves.
  Plans, bit-reversal maps, twiddles, and output work arrays are preallocated.
- The timed lookup path includes key packing from the actual decimated input
  order, the full table-row copy, and every upper merge. There is no input or key
  preprocessing omitted from execution timing.
- Key bit j is `input[global_bit_reverse(leaf_start + j)]`. Each table row stores
  the output after the corresponding bit-reversed leaf FFT. Contiguous natural
  input blocks would be incorrect for these radix-2 leaves.
- The full-spectrum tables occupy 1 KiB, 32 KiB, and 16 MiB for 4, 8, and 16 binary
  inputs, respectively. They contain 2^leaf_size rows of leaf_size complex doubles.
- Each sample cycles over 16 distinct seeded random inputs, with a whole number
  of cycles. No intermediate FFT outputs are reused. Method order is randomized
  each round, with warmup before measurement. Reported medians are medians of
  batch-average per-transform times, not single-call latency percentiles.
- Table allocate-and-populate and plan setup costs are measured separately.
  First allocation and repeated-build median are both recorded. No artificial
  cache flushing is done; these are not controlled cache-cold latency measures.
- The process is pinned to one available logical CPU if supported. This is a
  virtualized environment with uncontrolled neighboring load/frequency effects.
- NumPy/SciPy comparisons in `results.json` include their Python call and output
  allocation costs. The C result uses a preallocated output and excludes Python
  dispatch through a timed C batch. These are useful end-to-end context, not an
  allocation-matched library bake-off. `rfft` produces only half a spectrum and is
  labeled separately because it performs a different output task.

## Validation

The harness verifies every pattern in every table, including all 65,536 rows of
the 16-input table. It also compares all seven full FFT methods against NumPy on
zero, one, alternating, impulse, and five independently seeded random inputs,
across lengths 16, 32, 64, 128, 512 and the five measured lengths through 2^20.
There are 630 full FFT checks in the default run. Validation is outside timing.

`results.json` records the first 11-round run with practical library baselines.
`results_confirmation.json` records the longer 21-round C-only confirmation, including
raw samples, p10/p90 batch times, relative median absolute deviation, setup costs,
and speedups against both ordinary radix-2 and the best measured arithmetic
control. A null construction break-even means the lookup was not faster than
that arithmetic control; no positive amortization point exists in that run.

## Observed results on this environment

The longer confirmation run found the 8-input lookup about 1.20x and 1.08x faster
than the best arithmetic codelet at N=4,096 and N=16,384. Around N=65,536, the
8-input difference was small and changed sign between runs. At N=262,144 and
N=1,048,576, arithmetic 16-point codelets were about 6% faster than the 8-input
lookup in the confirmation run. The 16 MiB full 16-input table was substantially
slower for larger N. These are measured outcomes of this implementation, not a
universal crossover or a claim that lookup tables outperform tuned FFT libraries.

The construction median was about 0.46 microseconds / 2.23 microseconds / 1.61
milliseconds for the 4/8/16-input tables, with first observed constructions at
12.20 microseconds / 5.37 microseconds / 5.00 milliseconds. The very small table
setup numbers include ctypes overhead and should be treated as approximate.
For lookup8 at N=4,096, the median setup cost amortizes after roughly two FFTs;
using the first observed build cost, roughly three. If lookup is slower than an
arithmetic codelet, reuse cannot make its steady-state deficit disappear.

All full FFT correctness checks passed; worst absolute error was 2.25e-12.
The optional `test_sanitizers.c` checks memory/undefined-behavior safety and
cross-method agreement for every power-of-two size from 16 through 1,048,576.
See `sanitizer_result.txt` for the observed result.

The first sanitizer run could not complete LeakSanitizer under this sandbox’s
traced process. The rerun disabled leak detection with
`ASAN_OPTIONS=detect_leaks=0`; address and undefined-behavior instrumentation
remained enabled. Leak detection is therefore unverified.
