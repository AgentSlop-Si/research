# FFT Research — Phase 7: Persistent Factored Convolution Graph

**Status:** Runnable Python research prototype. Reproduces established algebraic identities and benchmarks a persistent, relation-aware implementation. **No new universal sub-`N log N` FFT or integer-multiplication theorem.**

This package carries forward Phase 5 (`cost_aware_fft.py`, `phase.py`) and Phase 6 (`relational_convolution.py`) and adds Phase 7 (`persistent_chain.py`). It supports chains of circular convolutions, immutable forked versions of the inputs, output frequency queries without an inverse FFT, and a linear-time full-output path after a *known sparse change to one factor*, once baseline and leave-one-factor-out convolutions are cached.

### Example

```python
import numpy as np
from persistent_chain import ChainEngine

n = 4096
engine = ChainEngine(max_complement_bytes=64*1024**2)
seeds = []
for offset in (3, 5, 7, 11):
    x = np.zeros(n)
    x[0] = 1.0
    x[offset] = 0.25
    seeds.append(engine.seed(x))  # precomputes one real FFT per new seed

original = engine.chain(seeds)  # circular convolution of all four signals
version_a = original.edit(0, 17, 2.0)
version_b = original.edit(0, 17, -3.0)

# Full outputs. A cached leave-one-out convolution is computed on demand.
result_a = version_a.dense()
result_b = version_b.dense()

# Query selected *frequency* bins without computing the entire spectrum.
four_bins = version_a.frequencies([0, 1, 17, 100])

# Query selected *time* convolution coefficients without full materialization.
two_coefficients = version_a.time([5, 25])

# They share unchanged canonical subtrees; old version remains unchanged.
print(original.count_reused_nodes(version_a))
print(engine.memory_report())
```


All arrays in this engine have the **same circular period `n`**. For exact linear convolution (before floating-point approximation), pad all operands so `n >= sum_i(len(x_i)-1)+1`, and do not mistake an undersized circular result for an unaliased linear one.

## Main API

- `ChainEngine.seed(values)` registers one immutable real vector and its cached `rfft`.
- `ChainEngine.chain(factors)` builds a balanced canonical binary product graph.
- `ChainVersion.edit(at, pos, delta)` returns a new version (original unchanged).
- `.shift(at, amount)` and `.scale(at, amount)` change one factor symbolically.
- `.convolve_with(other_version)` composes chains without dense intermediate output.
- `.frequencies(k_values)` returns only requested spectral bins.
- `.time(indices)` returns selected time-domain convolution coefficients; lazy for zero or one edited factor, otherwise materializes.
- `.dense(method='auto'|'sparse'|'native')` returns all `n` real output samples.
- `ChainEngine.from_phase5(states)` imports existing Phase-5 `SpectralState` objects. One-base cases reuse their immutable `rfft` and symbolic edits without re-FFT. Multi-base combinations currently fall back to one dense input materialization.

`auto` uses a simple conservative threshold of four accumulated edits to choose time-domain sparse reconstruction. This is not a measured universally optimal dispatcher.

## Key identities and constraints

For circular convolution `C = x_0 * ... * x_(m-1)` of real length-`n` arrays, let `C_{-j}` be the convolution of all factors except `x_j`. If factor `j` becomes `gain * roll(x_j, shift) + sum_t delta_t * e_t`, and all other factors are unchanged, then

```
C_new = gain * roll(C, shift) + sum_t delta_t * roll(C_except_j, t)
```

This is exactly true in ordinary algebra. After `C` and `C_except_j` are prepared, producing an explicit dense output needs `O(n(1+k))` arithmetic for `k` accumulated distinct edited positions; this is `O(n)` for constant `k`. It **does not** improve the cost of convolving arbitrary fresh inputs, and does **not** include preparation in the per-version bound. The saved transforms take `O(mn)` complex/real words.

When several factors are modified, **do not expand the product** into `2^m` terms. Evaluate the factored Fourier product and perform one inverse FFT when dense output is required. Frequency bins can be evaluated on demand. Current code supports `float64` inputs and approximate output, not bit-exact convolution.

## Reported benchmark (one sample local run)

48 forked versions, eight factors, one known edit per version, all `n` output coefficients materialized. Both paths prepare the eight input spectra; the comparator retains the unchanged factors' spectral product, but does not apply the specialized incremental update formula.

| n | Prepared FFT per version | Persistent reconstruction | Speedup |
| ---: | ---: | ---: | ---: |
| 4,096 | 2.29 ms | 1.94 ms | 1.18× |
| 65,536 | 39.53 ms | 11.50 ms | 3.44× |
| 262,144 | 269.88 ms | 81.97 ms | 3.29× |

For 128 different one-edit variants of a 128-factor chain, querying four frequency bins in the most recent run took **23.43 ms** for the generic persistent engine versus **6.98 ms** for an optimally specialized analytic leave-one-out comparator. This is a **negative result**: the general engine incurs nontrivial Python/object overhead even though the mathematical work is reduced. See `benchmark_results.json` for the raw definitions.

## Claim boundaries

This is a **dynamic, relation-aware** system. It uses known Fourier and convolution identities and a persistent DAG to organize them. It is not a new `O(n)` FFT on arbitrary unseen arrays, a drop-in implementation of OpenAI #130, or a new integer-multiplication bit bound. It does not have an eFFT head-to-head benchmark or a compiled-SIMD optimized backend.
