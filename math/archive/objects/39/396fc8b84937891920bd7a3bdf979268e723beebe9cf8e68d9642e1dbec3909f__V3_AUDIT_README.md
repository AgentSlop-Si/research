# Query engine v3: delta, validation, and minimal hardening

Audit date: 2026-10-08 UTC. Supplied research documents are dated 2026-10-09.

## What changed

The supplied `fft_relation_query_engine_v3(1).zip` adds five files to query v2:

- `view_optimizer.py`
- `tests/test_view_optimizer.py`
- `benchmark_view_optimizer.py`
- `benchmark_view_optimizer_results.json`
- `ADAPTIVE_VIEW_ORGANIZER_RESEARCH.md`

The only changed preexisting non-bytecode file is `README.md`, with ten added lines. Every preexisting Python source is byte-identical to `fft_relation_query_engine_v2(2).zip`. V3 therefore retains all previously identified v2 issues. It does not replace the separate Phase 7 persistent-convolution package.

The new idea in this revision is workload-adaptive consumer grouping: infer synchronization and frequency overlap, retain lazy spectral-union caches, and merge/split groups over time. It is complementary to single-view update coalescing and persistent convolution. It is a systems/data-structure refinement, not a new worst-case DFT complexity result.

## Delivered derivative and how to use it

The `hardened_overlay` directory is a complete v3 source tree. Its name records how it was constructed; no additional overlay is required to run it.

1. Start with the supplied v3 archive.
2. Overlay the audited v2 `arbitrary_output.py`, `multi_view.py`, and new `modular_phase.py`, plus `tests/test_hardening.py`.
3. Apply `organizer_hardening.patch` from the package root, or use the already-applied `hardened_overlay` directory.
4. Run `OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python3 -m unittest discover -s tests -v` from `hardened_overlay`.

Only two organizer behaviors were changed:

- Group replay collects only the missing event suffix by reverse traversal, then applies it in chronological order. This avoids scanning retained history while preserving floating-point accumulation order.
- Same-version group cache hits publish only the requested member. A genuine group refresh still publishes all members once, preserving current-view behavior.

Three regression tests cover suffix visitation count, chronological replay, and requested-member-only publication plus returned-array independence. No optimizer redesign, automatic migration policy, or new theoretical improvement is claimed.

Original input archives and extracted original sources were preserved. `archive_hashes.json` gives SHA-256 receipts; `delta_v2_to_v3.json` and `.patch` record the source delta. `hardened_v3_manifest.json` records derivative file hashes.

## Remaining limits and corrected accounting

### Planner work is not constant in consumer count

The base relation-state metadata update is expected O(1). The organizer wrapper can call the whole greedy replan inside `add_coefficient` or `add_point` at probe boundaries. It is therefore not a worst-case O(1) update when consumer count and planner state are parameters.

For C consumers in a fully merging case, the implementation performs C(C^2-1)/6 candidate evaluations plus one final group metric evaluation. Candidate metrics recompute frequency unions and pairwise history matching; each matching pass scans bounded query histories. Query histories are already version-ordered, but candidate member lists and installed union indices are sorted. Installing new groups builds index/take maps and may copy current caches. Preserving an unchanged numerical cache does not make the replan itself free.

Measured single probe-boundary update examples were 11/85/681/5,457 metric calls at C=4/8/16/32, taking approximately 0.16/0.95/8.29/99.33 ms in one instrumented run. These timings illustrate the omitted work, not a portable performance bound. Fixed configured C and bounded history hide that overhead in constants; they do not establish scalable constant-time updates. Replanning should be separately charged or incrementally budgeted before making a stronger bound.

### Replay, output, and scheduling costs

After the patch, one group refresh has the numerical replay/rebuild work plus publication of all member outputs once. A same-version cache hit has O(q_v) slicing/copying. The original repeated all-member publication added O(C times sum(q_v)) copying to a C-query burst. Both versions also pay query observation and occasional replanning.

The guard remains a heuristic. It omits copying/migration cost, does not fully account for history availability, and uses expected future queries that may not occur. There is no competitive or globally optimal partition guarantee.

### Memory and topology

Per-consumer query history is bounded, but `stats.partitions` appends indefinitely: 200 additional replans produced 201 stored partitions in the audit. The organizer's `storage_bytes` omits Python container overhead, query histories, and the partition-history list. Treat it as partial numeric-payload accounting, not total resident memory. Group selection remains memory-unconstrained.

The organizer assumes a fixed consumer topology. The underlying store exposes add/drop methods, but dropping a grouped view makes subsequent organizer queries fail, and adding a view then replanning before it is observed can fail. Both were reproduced as KeyError. Construct a new organizer after topology changes until lifecycle support is explicitly implemented.

### Floating-point caches are not literally identical

At equal versions, separate replay and rebuild paths can differ by roundoff. The audit measured a 6.43e-14 discrepancy on overlapping bins at the same version. Group seeding chooses one member's value per bin and does not reconcile discrepancies. The algebra is exact; the implementation has ordinary floating-point error, and ill-conditioned inputs warrant separate stability analysis. “Identical by construction” should be interpreted mathematically, not as a bitwise assertion.

## Next useful experiment

Keep the verified organizer fixes and hardened core. Before extending to overlapping, budgeted spectral groups, measure planner/migration cost and total memory explicitly; bound diagnostic history, define fixed versus dynamic view membership, and test adversarial schedule changes. Then evaluate memory-budgeted group selection with hysteresis against this baseline. The present numerical and timing evidence supports useful reuse in synchronized workloads, not a universal win.
