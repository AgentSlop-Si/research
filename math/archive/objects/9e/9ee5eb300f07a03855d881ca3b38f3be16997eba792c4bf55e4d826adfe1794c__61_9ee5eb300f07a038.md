# Phase 10 — Ahead-of-time compiled two-factor convolution updates

**Status: tested research implementation, not a new bound for arbitrary fresh FFTs or integer multiplication.**

Phase 10 extends the Phase 8–9 algebraic FFT project in two ways:

1. **Simultaneous edits to two separate input signals** in a canonical sum/convolution DAG, including mixed nonlinear terms such as `A*A*B` and `B*B`.
2. **Offline C++ compilation**, so the normal update path incurs no Numba JIT or compiler startup. A shape-specialized C++ evaluator is generated from a small validated list of algebraic degrees and built *before deployment*; unmatched shapes use a generic precompiled C++ evaluator or NumPy.

Both changes matter for persistent workloads with **known edit metadata** and **many related versions**. Source code and generated library are included for reproducibility. The prebuilt binary here targets Linux x86-64 and may require rebuilding on another system; Windows users can run under WSL with `g++`.

## Quick start

```bash
python -m pip install -r requirements.txt
# Run once during installation/deployment, not at execution time:
python build_native.py
python offline_codegen.py

python demo.py
python -m unittest discover -s tests -v
python benchmark.py
```

`build_native.py` creates the general `libfft_phase10.so`; `offline_codegen.py` produces `native_shape_a2b.cpp` and the optimized `libfft_phase10_shape.so` using `shape_manifest.json`'s algebraic signature. No external network access or nonstandard C++ libraries are required. Both are compiled using `g++ -O3` without unsafe `fast-math` assumptions.

**Python runtime requires NumPy + SciPy.** Numba is needed only for the inherited Phase 9 regression tests and legacy JIT implementation, not for the new Phase 10 native path.

```python
import numpy as np
from algebra_fft import AlgebraFFT
from two_edit_engine import prepare_two

n = 65536
rng = np.random.default_rng(22)
e = AlgebraFFT(n)
a, b, c, d = [e.signal(rng.normal(size=n)/np.sqrt(n)) for _ in range(4)]

# Circular convolution is denoted by `mul`; repeated A is intentional.
root = e.add(e.mul(a, a, b), e.mul(a, b), e.mul(b, b), e.mul(c, d))
plan = prepare_two(e, root, a, b)

# Two simultaneous known edits, each relative to the unchanged baseline.
whole = plan.update(pos_a=100, delta_a=.05, pos_b=900, delta_b=-.03)
selected = plan.update(100, .05, 900, -.03, indices=[1, 5, 999])

print('AOT shape matched:', plan.shape_available)
print('Prepared bytes:', plan.memory_bytes)
```

The returned `whole` contains all N **time-domain circular-convolution output coefficients**, not Fourier frequency bins. For linear (non-circular) convolution, pad signals sufficiently first. The engine only handles real float64 values and is not an exact arbitrary-precision integer-multiplication package.

## The exact algebraic identity

For any polynomial expression `F(A,B)` built from addition, scalar multiplication and circular convolution,

\[
F(A+\alpha e_s,B+\beta e_t)[q]
=\sum_{h,l}\alpha^h\beta^l K_{h,l}[(q-hs-lt)\bmod N],
\]

where `K[h,l]` are cached symbolic expansion coefficients and `e_s` is an impulse at index `s`.

For the demonstrated expression `F=A*A*B+A*B+B*B+C*D`, the nonzero coefficients are:

| Degrees `(h,l)` | Coefficient kernel `K[h,l]` |
|---|---|
| (0,0) | `A*A*B+A*B+B*B+C*D` |
| (1,0) | `2*A*B+B` |
| (0,1) | `A*A+A+2*B` |
| (2,0) | `B` |
| (1,1) | `2*A+e0` |
| (0,2) | `e0` |
| (2,1) | `e0` |

The `(1,1)` and `(2,1)` contributions are **mixed interactions** between the two edits. Leaving them out gives incorrect results, even if each single-factor formula is individually correct.

The compiler keeps provably sparse impulse coefficients as sparse point updates. It does *not* guess sparsity by thresholding tiny floating-point values.

## Complexity and limits

If the expression's degree is bounded, and `D` dense correction kernels plus `S` sparse impulse corrections are prepared, then the online full-output cost is `O(N D + S)` and a selected `Q`-coefficient query uses `O(Q(D+S))` in the current partial-output loop. Stored dense kernels require `O(ND)` words. Preprocessing costs FFTs, symbolic graph work, and one inverse transform per dense kernel and must be included in cold or amortized comparisons.

For constant degree `D,S`, full reconstruction is `Theta(N)`, optimal up to constants for explicitly writing N outputs. **This is a dynamic prepared-workload statement only**; fresh unrelated inputs require regular transforms. The generic offline C++ routine handles other shapes without runtime compilation, but may be slower than a bespoke kernel.

## Benchmark

`benchmark.py` measures the same full-output problem using: two new SciPy FFTs plus a prepared fixed factor `C*D`; existing Phase 8 NumPy coefficient kernels; general AOT C++; generated shape-specialized AOT C++; and an independently hand-coded C++ update for this exact expression.

Results in `benchmark_results.json` were measured as local medians across five runs with 48 independently branched versions. The cold Phase 10 total includes input FFTs, graph preparation, both library loads and the stream. **It excludes the separately reported offline `g++` build**, which is a deployment cost. The SciPy baseline pays for its fixed `C*D` preparation during its timed stream, but does not precompute both edited-factor spectra. No universal wall-clock superiority is claimed.

| N | SciPy 48 versions | AOT shape warm | Phase 10 setup | AOT shape cold total | Cold ratio |
|---:|---:|---:|---:|---:|---:|
| 4,096 | 3.438 ms | 0.987 ms | 1.471 ms | 2.458 ms | 1.40x |
| 65,536 | 54.070 ms | 6.780 ms | 7.265 ms | 14.045 ms | 3.85x |
| 262,144 | 268.300 ms | 24.335 ms | 22.076 ms | 46.411 ms | 5.78x |

At 262,144 points, the handwritten C++ baseline used 22.862 ms for the same 48 warm outputs. The automatically generated specialized code was about 6.4% slower, while the generic native evaluator needed 47.059 ms. Two affine correction coefficients are prepared directly from stored signals in O(N) work, rather than through inverse FFT. Small-workload performance and numbers will vary by machine.

## Project files

- `two_edit_engine.py`: bivariate symbolic compiler, numerical coefficient preparation, AOT dispatch, partial queries, bounds.
- `native_kernel.cpp` and `build_native.py`: generic precompiled native evaluator and hand-coded comparison kernel.
- `offline_codegen.py`: bounded, validated degree-signature generator and **offline** build.
- `native_shape_a2b.cpp`, `libfft_phase10_shape.so`, `shape_manifest.json`: generated and built demonstration specialization.
- `algebra_fft.py`: reused Phase 8 canonical graph/FFT preparation.
- `compiled_kernels.py`, `auto_dispatch.py`: inherited Phase 9 research code for comparison (Numba JIT, not used by Phase 10).
- `benchmark.py`, `benchmark_results.json`: full-output performance comparison.
- `tests/test_two_edit.py`: independent SciPy checks, 384 modular test cases using schoolbook convolution, error paths and sparse-structure assertions.
- `RESEARCH.md`: derivation and limitations.

These techniques are based on classical convolution algebra and automatic differentiation / Taylor-mode ideas. The work is a research prototype and an engineering improvement, not a claimed improvement to OpenAI #130's fresh exact-DFT exponent or CrocSwap's general integer-multiplication bound.
