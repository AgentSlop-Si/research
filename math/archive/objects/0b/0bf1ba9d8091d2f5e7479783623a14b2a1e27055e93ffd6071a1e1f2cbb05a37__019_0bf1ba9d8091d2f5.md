# Phase 6 — Persistent convolution and exact dynamic products

**Date:** October 9, 2026  
**Research status:** Implemented, regression tested, benchmarked in a specific environment, algebraically audited over finite fields. **Not** a new universal sub-`N log N` FFT or a fresh integer-multiplication exponent result.

## 1. What changed relative to Phases 1–5?

Earlier phases optimized or reused *Fourier transforms*. Phase 6 instead observes that a related product can often be updated directly in the **time domain**, avoiding even the forward/inverse FFT. We compose Phase 5's persistent relation representation with the circular-convolution bilinear map. This yields (1) new explicit-output reconstruction, (2) selected output queries, (3) time-domain subscriptions under edits to **either** operand, (4) an exact integer bit-flip product tracker, and (5) an online native-versus-reuse crossover calibration.

The underlying algebraic properties are classical. The contribution *within this project* is combining them into a cost-aware persistent engine and giving reproducible performance boundaries.

## 2. Exact algebraic identity

Let `R_s` denote a circular right shift by `s` and `e_p` the length-`N` impulse with a single 1 at index `p`. Over any commutative ring, write

    A = sum_i alpha_i R_si(U_i) + sum_{p in P} a_p e_p
    B = sum_j beta_j  R_tj(V_j) + sum_{q in Q} b_q e_q.

Circular convolution is bilinear, with

    R_s(U) * R_t(V) = R_(s+t)(U*V)
    e_p * U = R_p(U)
    e_p * e_q = e_((p+q) mod N).

Therefore

    A*B = sum_(i,j) alpha_i beta_j R_(si+tj)(U_i * V_j)
        + sum_(i,q) alpha_i b_q R_(si+q)(U_i)
        + sum_(p,j) a_p beta_j R_(p+tj)(V_j)
        + sum_(p,q) a_p b_q e_((p+q) mod N).

Store `U_i * V_j` only once per unordered pair of immutable basis objects. The implementation uses their previously cached real FFT spectra to calculate this core convolution with one inverse FFT per newly encountered pair.

For **one changed input sample** in A, B fixed,

    C' = C + delta * R_t(B).

For the general case, **both** operands can change; the fourth line above accounts for the cross-product of their sparse corrections. Dropping it would give wrong answers.

## 3. Complexity with explicit accounting

Let `r_A`, `r_B` be numbers of basis/shift terms and `k_A`, `k_B` be numbers of distinct pending sparse changes.

Assume cached cores for all `r_A*r_B` base pairs and supplied exact relationship metadata. Then:

| Operation | Arithmetic operations, warm | Extra work / notes |
|---|---|---|
| Dense convolution (entire N-vector) | `O(N*(1+r_A*r_B+r_A*k_B+k_A*r_B) + k_A*k_B)` | Writes `Omega(N)` output values |
| One time-domain coefficient | `O(1+r_A*r_B+r_A*k_B+k_A*r_B+min(k_A,k_B))` | Build two sparse hash indices once per view in `O(k_A+k_B)` |
| Q selected spectral product bins | `O(Q*(r_A+r_B+k_A+k_B+1))` | Needs cached spectra for bases |
| Subscribe to Q time coefficients | `O(Q*(r_other+1))` per known edit | Opposite edit map queried by index; Q outputs only |
| Preprocess a new base pair | `O(N log N)` | Uses two already registered real FFTs and one inverse; registration itself costs additional FFTs |

For the common one-base/one-fixed-kernel/one-edit family, after the initial core is cached, each **dense** variant takes `Theta(N)`. If `M` such variants are explicitly output, total cost is `O(N log N + M N)` in the conventional arithmetic model. The `Omega(M N)` output-size lower bound means this is output-optimal *for this restricted family*, up to the initialization term. This is not a new lower bound or general FFT theorem.

A single *selected* coefficient after the base core is cached is `O(1)` for one known changed sample. The family of possible queries and the preprocessing requirement must not be conflated with a fresh arbitrary transform.

Memory: Each real basis signal uses about `8N` bytes plus about `8N` bytes for a real-to-complex spectrum. One cached base-pair circular convolution uses `8N` bytes. Two bases plus one core use about `40N` bytes (before Python headers/temporaries). The engine's core LRU budget applies only to core products, not bases retained by caller state handles. Persistent variants store `O(r+k)` metadata each unless dense output is requested. Calibration caches cost profiles and their training cost must be amortized over future calls.

## 4. Exact integer multiplication after a bit flip

For nonnegative integers `A,B` with `n`-bit operands and cached `P=A*B`, flipping bit `t` of A gives

    P' = P + sign*(B << t), sign=+1 if 0->1, -1 if 1->0.

Similarly for a bit flip in B, use the *current* A. The calculation uses `O(n)` bit operations in a conventional bit-cost model to form a shift/add/subtract of `O(n)`-bit values, with a previously stored product. It works exactly even when carries propagate across the whole product. A fresh `A*B` is still required at initialization. For `k` known bit edits, straightforward updates use `O(k n)` bit operations; a fallback to a full multiplication is preferable for sufficiently large `k`. This is a classical dynamic-product identity, not a claim of faster fresh integer multiplication.

The `DynamicBitProduct` Python reference program tracks both operands and includes validation against Python's actual big integer product. It does not claim to implement a fixed-tape Turing machine or OpenAI #109 or #130.

## 5. Numerical vs exact verification

The NumPy/SciPy circular-convolution implementation is numerical (float64). Our complete algebra was also verified independently in `exact_modular_audit.py` for **1,600 randomly generated cases** over prime moduli 3, 5, 97 and 65521, including shifted bases and sparse changes in both operands. This validates the stated reconstruction identity for the sampled instances, not all mathematical theorems in the larger project. The big-integer tracker is exact and is compared directly to recomputation over randomized bit flips.

The inherited 19 Phase-5 tests plus 14 new Phase-6 tests pass (33 total). See `tests/` and execute from the project root.

## 6. Benchmarks: dense circular convolution

All timings are **local**, with single-thread Python/SciPy/NumPy and NumPy-generated random inputs. The baseline transforms the changed operand with SciPy rFFT and multiplies by a **precomputed** fixed-kernel spectrum, then calls inverse real FFT. The Phase-6 method registers both bases, computes the cached core, and reconstructs each variant by shifted kernel addition. **Both** include initial preparation in the timed region; all variants produce full dense length-`N` outputs. Three-run median. See `benchmark_results.json` for exact values.

| N | Variants | Prepared-kernel FFT, ms | Phase 6, ms | Speedup |
|---:|---:|---:|---:|---:|
| 4,096 | 48 | 2.172 | 0.915 | 2.37x |
| 16,384 | 48 | 9.156 | 1.588 | 5.77x |
| 65,536 | 40 | 30.077 | 5.104 | 5.89x |
| 262,144 | 32 | 179.704 | 20.695 | 8.68x |
| 1,048,576 | 20 | 551.927 | 83.107 | 6.64x |

The speedup is **not** monotone. It is a workload/implementation result, not a general asymptotic wall-clock theorem.

## 7. Warm reconstruction crossover / negative result

The warmed-core experiment (`crossover.py`) shows that shifted kernel additions stop winning when there are too many independent edits. The baseline was again a prepared-kernel FFT, not two entirely fresh FFTs.

| N | Last measured k with >1x reuse speedup | k with measured slowdown |
|---:|---:|---:|
| 4,096 | 8 (1.04x) | 16 (0.58x) |
| 65,536 | 16 (1.33x) | 32 (0.78x) |
| 262,144 | 32 (1.20x) | 64 (0.73x) |

These are **empirical** thresholds affected by CPU, memory bandwidth, signal structure and SciPy version, not a mathematical formula. `RelationalConvolver.calibrate_sparse` can measure candidate edit counts at runtime and store a warm threshold. Its returned receipt includes calibration time and core initialization. The default `auto` heuristic uses the trained cutoff if available, otherwise takes a conservative path. For other shapes with no fixed operand, it can use native FFT.

The strong lesson: the number of pending edits is itself a cost parameter. Reuse must be abandoned once dense recomputation becomes cheaper.

## 8. Partial-output subscriptions

With Q subscribed circular-convolution output positions, one known edit `A[t] += delta` changes each requested time coefficient `C[q]` by

    delta * B[(q-t) mod N].

Likewise one edit of B uses the **current A**. This is O(Q) work for a fixed single-basis opposite operand even after thousands of earlier edits, because the other operand is accessible through a persistent sparse dictionary. The implementation permits edits to both operands, where the opposite sparse residual is accessed through an indexed map.

At N=65,536, Q=4 and 320 alternating-operand edit events, selected coefficient subscription took 7.223 ms including two initial basis FFTs, core preparation, and a final extra native convolution validation. Direct recomputation of the same Q requested time coefficients using NumPy dot products took 304.686 ms. This is a **42.2x** speedup relative to that comparator, not a speedup over all possible dynamic-query algorithms. Both sides produce Q requested coefficients per event. The subscribed path actually did extra final verification inside its timed section. See `subscription_results.json`.

## 10. Closest known literature and what's distinctive

The **event-based FFT** (Tapia et al., 2024) and **eFFT-C++** (2026) cache intermediate FFT trees and update them when event streams change. Our Phase-6 implementation instead uses algebraic persistent operands and *cached products* to answer convolution-output queries and materialize related products. No direct eFFT benchmark has been run; this is not a proven novel algorithmic advantage.

- eFFT: https://github.com/raultapia/efft
- Reif & Tate, *On Dynamic Algorithms for Algebraic Problems* (1997): https://doi.org/10.1006/jagm.1995.0807
- Frandsen, Hansen & Miltersen, *Lower Bounds for Dynamic Algebraic Problems* (2001): https://doi.org/10.1006/inco.2001.3046
- OpenAI #130 scope: https://github.com/openai/math/blob/main/lean/docs/130.md
- OpenAI #109 (different fixed-tape multiplication model): https://github.com/openai/math

No new asymptotic result for multiplying two arbitrary previously unseen integers and no unrestricted sub-`N log N` complex DFT has been demonstrated. A claim of novelty would require a careful comparison against dynamic convolution and algebraic data structures.

## 11. Next falsifiable research direction

The next important target is **compressed downstream operators**: rather than materializing `A*B` after every version change, keep the output as (base-core identity, shifted basis terms, sparse corrections) and pass it into a subsequent linear filter or product. A large chain of operations could reuse intermediate results but also risks term-count explosion. The concrete question is whether we can keep representation size under control (algebraic normal-form simplification, canonicalization, bounded rebasing) while maintaining an end-to-end sub-full-transform cost with accurate memory accounting.

A second target is a *workload-optimal dispatcher* under mixed edit/query distributions. We have measured empirical crossover, but not proved a competitive ratio relative to the best schedule of native FFTs, cached kernels, or persistent partial queries, including all calibration overhead.
