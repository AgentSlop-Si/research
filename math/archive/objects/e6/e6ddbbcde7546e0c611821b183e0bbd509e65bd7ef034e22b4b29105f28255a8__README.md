# Phase 9 — Compiled algebraic FFT-update kernels

**Status:** tested numerical research software; NOT a faster worst-case arbitrary FFT, and NOT a new integer-multiplication exponent.

Phase 9 continues the Phase 5–8 persistent Fourier/convolution work. It compiles symbolic single-sample update polynomials from the existing Phase-8 `AlgebraFFT` graph into shape-specialized, fused loops and (optionally) JIT-compiles them with Numba. It avoids allocating one `np.roll` array per convolution kernel, and applies mathematically sparse impulse corrections as point updates. An auto planner guards against the cold JIT penalty for small workloads.

## Small example

```python
import numpy as np
from algebra_fft import AlgebraFFT
from compiled_kernels import compile_expression
from auto_dispatch import plan_auto

N=65536
rng=np.random.default_rng(123)
e=AlgebraFFT(N)
a,b,c,d=[e.signal(rng.normal(size=N)/np.sqrt(N)) for _ in range(4)]
# The same input a appears three times in one product.
root=e.add(e.mul(a,a,a),e.scale(e.mul(a,b),2),e.mul(c,d))
compiled=compile_expression(e,root,a,backend='numba',max_degree=3)
result=compiled.single(100,0.01)                  # N full output coefficients
selected=compiled.single(100,0.01,[0,17,999])    # only 3 requested coefficients

prepared=e.prepare(root,a,max_degree=3)
auto=plan_auto(prepared,expected_versions=48)
print(auto.mode, auto.reason)                    # likely stays on NumPy for cold short stream
```

## What is generated?

For `F(A)=A*A*A+2A*B+C*D`, the symbolic jet coefficients are:

- `K0=A*A*A+2A*B+C*D`, dense base;
- `K1=3A*A+2B`, dense convolution kernel;
- `K2=3A`, dense convolution kernel;
- `K3=e0`, one unit impulse (no dense array needed).

The compiled hot loop implements for a known edit `(position=t, delta=δ)`:

`F(A+δe_t)[q] = K0[q] + δ K1[(q−t)%N] + δ² K2[(q−2t)%N] + δ³ 1_{q=3t mod N}`.

Output order, all shifts and coefficients are generated from the Phase-8 symbolic degree expansion rather than user-written casework. The generator emits only validated integer degrees and numeric array accesses (bounded to degree ≤ 8 by default), never arbitrary source text supplied by a caller. It does NOT synthesize a globally optimal code schedule.

### New modules

- `compiled_kernels.py`: deterministic loop generator, optional Numba JIT, output validation, dense/sparse kernel metadata, source inspection, per-shape compiled-code caching.
- `auto_dispatch.py`: simple short-stream guard plus calibration against Phase-8 NumPy update. Charges compilation/calibration in its decision. Does not claim optimal threshold selection.
- `tests/test_compiled_kernels.py`, `tests/test_auto_dispatch.py`: numeric, exact modular, bounds, error-path tests.
- `benchmark.py`: same-scope cold/warm comparison against both SciPy recomputation and a hand-specialized Numba implementation; includes full-array numerical validation and coefficient-query comparisons.
- `RESEARCH.md`: proofs, hardware-cost caveats, numerical/model limitations, next experiments.
- `COMPARE_EFFT.md`: prior art and fair workload scope for eFFT.

## How to interpret timings

- **Cold total** = seed FFTs + symbolic preparation + generated-code compilation (or explicit hand-written Numba JIT) + one stream of 48 versions. The first JIT compile can be hundreds of milliseconds; a 4,096-point cold session loses dramatically.
- **Warm stream** = only the 48 transformed versions, after everything has been prepared. This is useful in persistent, repeatedly edited workloads, not equivalent to cold-start FFT time.
- **Partial output** = six chosen time-domain convolution coefficients, not a whole Fourier transform. Compare partial output only against an identical six-coefficient baseline.
- The generated fused loop is often near the hand-specialized Numba loop. Neither should be compared with eFFT's 2D event FFT without converting to an identical operation and output scope.

A numerical graph compiled at time `t0` can be reused only while base inputs remain immutable and each edit is interpreted **relative to the same base**, not accumulated sequentially unless the pending changes are separately represented. The code supports one known edit per version; arbitrary new dense inputs still require a fresh full transform. No correction is derived from float-based numerical zero testing.
