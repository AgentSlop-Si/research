# Phase 5 technical research and falsifiable claims

**Date:** October 9, 2026. **Scope:** dynamic/adaptive real FFTs with producer-provided relations, not an improved fresh arbitrary DFT upper bound.

## 1. Unified relation representation

A state of length N is described by immutable cached real basis signals b_t and their spectra F(b_t), real scalars c_t, cyclic right-shifts s_t, and a sparse correction e:

    x[j] = sum_t c_t * b_t[(j-s_t) mod N] + e[j].

Therefore, with omega = exp(-2*pi*i/N),

    F(x)[q] = sum_t c_t * omega^(q*s_t) * F(b_t)[q]
                + sum_{j in supp(e)} e[j] * omega^(q*j).

No new FFT is necessary to evaluate any bin if base spectra are already known. This identity is exact in algebra; the implementation uses numerical `rfft` arrays. It holds for every input satisfying its *supplied relation*, not all unrelated inputs.

- `r` terms and `k` nonzero pending edits: one bin is `O(r+k)` arithmetic, Q selected bins are `O(Q(r+k))`.
- Materializing all bins by direct accumulation is `O(N(r+k))`, including output memory traffic.
- `fork()` copies O(r+k) metadata but no N-element signal or spectrum.
- A known shift updates only the term offsets and pending-edit indices, O(r+k).
- A known edit updates a dictionary entry in expected O(1); repeated edits to one index merge.
- `TrackedBins` keeps Q selected bins updated in `O(Q)` arithmetic per producer-specified edit, rather than summing all previous edits on every query.

Neither `O(Q)` event cost nor `O(r+k)` frequency-query complexity includes discovering the edit from an arbitrary new dense array. We do **not** make that detection assumption silently.

## 2. Pruned sparse-delta transform, and why it can lose in practice

Suppose delta has k nonzero entries and N=b*m where b=2^ceil(log2 k) is a power of two, N is a power of two, and m=N/b. For each changed sample at t=r+b*l, construct

    V[q,r] += delta[t] * exp(-2*pi*i*q*t/N),  0<=q<m.

Then, for 0<=j<b,

    D[q+m*j] = FFT_b(V[q,:])[j].

Proof: substitute output index q+m*j into the DFT and use exp(-2*pi*i*j*l)=1. The remaining r-dependence is precisely a length-b Fourier transform.

Filling V costs O(m*k) <= O(N); reading/writing it costs O(N). The m independent size-b FFTs cost `O(N log b)=O(N log(k+1))` arithmetic. Thus the sparse correction has a *theoretical* `O(N(1+log(k+1)))` arithmetic bound in an FFT arithmetic model, plus O(N) memory. This is classical sparse/pruned FFT reasoning, not a novel algorithm. Our vectorized code stores 16N bytes for V and uses SciPy along the b dimension. Despite fewer theoretical butterflies, these extra arrays often make it slower than a highly optimized full `rfft`.

Using the exact-arithmetic #130 theorem **as a theoretical subroutine**, the same algebra gives an exact-model `O(N(1+(log(k+2))^(1-delta)))` bound with delta=1e-13 (in #130's strict model, and with all preparation charged as in its uniform theorem). **We do not implement #130**, nor claim the bound for SciPy floating-point software or bit complexity.

## 3. Actual measured dispatch choices

The hardware profiler times the candidates **including reconstruction and memory costs**, rather than only arithmetic counts. It validates every measured result against fresh SciPy output. It stores the winning strategy for a matching (N, k, r, shifted) shape. Profiles estimate steady-state/warm-query performance and are not stable across CPUs or library versions.

Saved `benchmark_results.json` contains medians, software versions, and the seed. Run `OPENBLAS_NUM_THREADS=1 python benchmark.py` to regenerate. The 4-bin query result is **not** comparable to a method that also computes only four bins, and thus cannot establish a broad FFT speedup by itself.

Caution: repeated edit and fork benchmarks include initial reference FFT and materialized spectra, whereas bin subscription deliberately does NOT materialize full output after each edit. The latter is a different API task.

## 4. Memory accounting

- Dense baseline base x and base rfft: about 8N + 16*(floor(N/2)+1) ~= 16N bytes.
- Optional phase vector for one position: about 16*(floor(N/2)+1) ~= 8N bytes, bounded by LRU cache.
- Individual live SpectralStates share bases and hold O(r+k) metadata unless the caller opts to store dense output.
- Pruned V: N complex128 entries ~= 16N bytes, plus backend temporaries (separately accounted by system allocations).
- Exact-result cache hashes bytes (O(N) reading), verifies full equality, and stores bounded references. Hash collisions cannot cause incorrect results.
- Caller-held live states and their immutable bases are not included in the engine's internal LRU budgets; a quota controlling caller-owned handles would require a higher-level reference manager.

Memory traffic and output materialization often dominate runtime once all butterfly operations have been optimized.

## 5. Relation to earlier phases and external work

Phase 1: canonical DAG and collisions; helped repetitive inputs but random-input reuse stopped scaling.
Phase 2: split radix, known 1/3 reduction in nontrivial complex twiddle counts; no new exponent. Exact finite-field WHT tabulation reaches O(N log N/log log N) in the appropriate RAM model, as already known from Alman.
Phase 3: compiled-C++ experiment showed that relation search and materializing dense outputs, not only Python dispatch overhead, were bottlenecks.
Phase 4: sparse-edit, shared-base fork, phase tiling and lazy bins. Phase 5 unifies them behind an explicit state-based dispatcher and adds measured cost selection, small k pruned alternative and frequency subscriptions.

## 6. Next falsifiable hypotheses

1. **Persistent radix-2 DAG with producer notifications:** May beat lazy phase accumulation for densely subscribed frequencies at low event rates, but must count cache traffic, construction and event scheduling. Compare directly to eFFT.
2. **Compressed-output consumers:** Feed the `(coefficients, basis spectra, pending sparse edits)` representation into a downstream frequency-domain operation without materializing every intermediate spectrum; measure end-to-end speedups in convolution/filtering workloads.
3. **Adaptive online calibration:** Calibrate periodically and amortize calibration over many future requests, with confidence bounds and nonstationary workload detection. Measure cost of calibration itself.
4. **Phase cache optimization:** Batch/merge repeated positions and vectorize updates while limiting accumulated floating-point error; incorporate automatic rebasing after long event streams.
5. **Native C++/SIMD kernels:** Avoid Python per-event and Python per-signal overhead and benchmark against real `rfft` libraries and eFFT on comparable tasks, sizes, precision and hardware.
6. **#130 integration:** Needs an actual verified implementation of OpenAI's exact arithmetic DFT and a strict model translation; replacing SciPy numerics with the theorem symbolically is not a practical backend port.

**Research boundary:** No newly proved sub-N-log-N algorithm for arbitrary fresh FFT, no published novelty claim, and no new exact integer-multiplication bit bound.
