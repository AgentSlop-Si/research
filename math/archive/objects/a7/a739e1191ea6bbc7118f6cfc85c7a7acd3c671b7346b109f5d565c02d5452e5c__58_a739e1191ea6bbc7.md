# Phase 10 research audit: simultaneous two-factor convolution edits and AOT kernels

October 9, 2026. **Status: algebraically valid dynamic update; executable numerical implementation; no new fresh-FFT complexity theorem.**

## 1. Why a bivariate jet is necessary

In a convolution ring R (e.g. length-N circular sequences over a commutative field), let F(A,B) be a polynomial expression built with additions and convolutions. Substitute two formal variables U and V:

    F(A+U,B+V) = sum_{h,l} K[h,l] * U^{*h} * V^{*l}.

The coefficient K[h,l] depends only on unchanged baseline A, B and other factors. This polynomial identity is exact, can be derived recursively over the expression DAG, and permits repeated A or B factors. If the edits are impulses `U=alpha e_s` and `V=beta e_t`, then `e_s*e_t=e_(s+t mod N)` and hence

    F(A+alpha e_s, B+beta e_t)[q]
      = sum_{h,l} alpha^h beta^l K[h,l][(q-hs-lt) mod N].

This formula handles all mixed orders including h*l>0. In general, independently combining two single-edit formulas would omit cross terms and be incorrect.

### Example and exact coefficients

For F(A,B,C,D) = A*A*B + A*B + B*B + C*D,

    K00 = A*A*B + A*B + B*B + C*D
    K10 = 2 A*B + B
    K01 = A*A + A + 2 B
    K20 = B
    K11 = 2 A + e0
    K02 = e0
    K21 = e0.

No other coefficient is nonzero. A symbolic zero is not inferred from small float magnitudes: the compiler uses exact graph operations and the previously implemented deterministic impulse recognizer.

## 2. Compiler and cost analysis

Given DAG with E nodes and bounded combined algebraic degree d, recursively attach a dictionary indexed by (h,l) to each node. Leaves A and B are respectively `A+U` and `B+V`; other leaves are constant in U,V; additions combine matching dictionaries and convolutions use polynomial multiplication. The number of bivariate monomials is at most (d+1)(d+2)/2. Degrees > configured bound or too many terms are rejected, never silently truncated.

Numerical coefficient kernels are evaluated by reusing Phase 8's existing Fourier-transform cache and inverse-transformed into real sequences. Each non-sparse coefficient requires up to O(N log N) for its inverse FFT, plus O(EN) graph evaluation in simple worst-case accounting; preprocessing, cache allocations and metadata are separate from online costs.

Let D be the number of nonzero **dense** coefficient kernels and S the number of sparse impulse correction entries (excluding the baseline). Then:

- Dense output materialization is O(N D + S) after preparation, with at least Omega(N) output writes.
- Q selected coefficients cost O(Q(D+S)) in the current implementation (sparse corrections are scanned for each requested index).
- Prepared dense arrays need O(N D) words; the FFT seed/cache may require further space.
- Cold use must include input FFTs, symbolic preparation, coefficient inverse transforms, and offline compilation if the binary was not previously deployed.
- No claim applies to arbitrary fresh unrelated A, B without paying those costs.

For the showcased example, D=4 dense corrections plus 2 symbolic impulse corrections, and the baseline K00. The prepared arrays contain O(5N) double values. An additional direct affine evaluator proves that K11 and K20 can be prepared by O(N) combinations of stored signals, rather than by an inverse FFT. Note that K11 contains a dense `2A` part **and** an impulse; this implementation stores the entire mixed coefficient densely. Further decomposition could save some arithmetic, but is not required for the stated bound.

## 3. Native compilation contract

Phase 9 generated Python bytecode and optionally ran Numba JIT, which was beneficial for a warm session but expensive for a cold one. Phase 10 instead distributes two native libraries built *before* the application starts:

1. Generic AOT C++ evaluator for arbitrary validated bivariate coefficient lists.
2. Shape-specialized AOT C++ evaluator generated offline from the bounded degree signature `(0,1),(1,0),(1,1),(2,0)` and sparse signatures `(0,2),(2,1)`.

The specialized library embeds **no numerical inputs**, FFT output values, input sizes or secret data. It embeds only coefficient degrees. The runtime checks the prepared symbolic signature against its manifest and passes the actual coefficients as contiguous arrays. The native library is called using `ctypes.CDLL`, not a runtime compiler. No Numba JIT or Python `exec` is used by the new Phase 10 path. On an unsupported or unmatched shape, the algorithm selects the generic AOT library or NumPy fallback.

The build requires a C++17 compiler with `__int128` (GCC/Clang); generated binary is platform-specific. There is no portable precompiled binary across Windows/macOS/Linux. On Linux, C++ compilation took approximately 0.315 seconds for the generic library and 0.167 seconds for the generated shape in this development environment. These costs are excluded from online cold-start timing because the binary already exists; they must be included in an end-to-end first build-from-source accounting.

## 4. Benchmarks and caveats

`benchmark_results.json` records five-run medians at N=4096, 65536, 262144 with 48 versions. All versions represent two simultaneous independent edits to a fixed baseline; both implementations output complete circular convolutions. Fresh SciPy baseline recalculates A and B FFTs and an inverse transform, reusing only C*D's fixed spectrum. Prepared Phase 10 includes the initial four input FFTs, symbolic coefficient construction, native load and 48 outputs. This is an intentionally stricter cold-start accounting for Phase 10.

**N=262144:**

- SciPy 48 versions: 268.300 ms.
- NumPy prepared jet, warm: 38.966 ms.
- Generic AOT, warm: 47.059 ms.
- Generated AOT shape, warm: 24.335 ms.
- Hand-written C++ native implementation, warm: 22.862 ms.
- Generated AOT prep + stream: 46.411 ms, about 5.78x faster than baseline in this measured workload.

Across small N and different hardware, setup can dominate, so speedup is not monotonic or guaranteed. The compiler backend is slower than the hand-written comparator by ~6.4% in this run. There is no eFFT numerical comparison: eFFT's event-driven FFT output is not the same problem as an arbitrary convolution-expression update.

**Precision:** All timing benchmarks are float64 and checked against SciPy. One example at N=262144 had max absolute difference ~1.21e-17. This is empirical numerical agreement, not a worst-case error certificate. A separate set of 384 small-sized independent integer-convolution cases, reduced modulo several primes, checked the algebra including simultaneous changes at the same position; each was evaluated with both NumPy and native code. Those are exact-identity checks with small integers and representable float64 intermediates; the native engine itself is not a finite-field arithmetic implementation.

## 5. Research boundary

The engine automates known algebraic identities. It doesn't beat general arithmetic bounds for fresh DFT or integer multiplication. To outperform existing event-based processing, it must demonstrate benefits from *arbitrary bounded-degree sum-product DAGs*, especially those with shared factors and multi-target edits that existing specialized algorithms do not already optimize. It also needs objective workload-specific comparisons and meaningful cost accounting for graph discovery and dense-output materialization.

Potential next experiments:

- Factor dense-plus-impulse K11 into a sparse component plus a dense component to reduce unnecessary array loads.
- Autotune the crossover between generic AOT, specialized AOT, NumPy, and full SciPy without hiding calibration cost.
- Generalize the bivariate jet compiler to multiple edited factors but bound its coefficient explosion and only materialize demanded output coordinates.
- Demonstrate a real task (dynamic filtering, streaming polynomial features, or updateable convolution networks) and compare against an optimized manually maintained incremental implementation.
- Implement an exact-integer or finite-field backend with explicit cost for coefficient growth and memory use.

## 6. Prior art

Bivariate polynomial expansion in a commutative algebra, FFT convolution and Taylor-mode automatic differentiation are standard mathematical techniques. The new implementation is a reproducible engineering composition, not a claim of novelty in those ingredients. OpenAI #130 is a separate exact-DFT result in an unrestricted complex arithmetic model; CrocSwap studies exact integer-multiplication bounds and rank-weighted circuits; neither is directly superseded by these amortized relation-aware update costs.
