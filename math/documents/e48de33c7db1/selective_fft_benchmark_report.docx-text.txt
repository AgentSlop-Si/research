Adaptive binary FFT implementation

Runnable implementation and held out validation | 8 October 2026

The implementation now offers a reusable binary FFT plan with a size dependent kernel choice. For one or a few transforms, use the explicit fixed arithmetic plan to avoid calibration. Optional autotuning compares arithmetic and small lookup kernels once, then reuses its decision. It chose the fastest held-out kernel at three of five sizes; its conservative rule skipped smaller gains at the other two.

Use the fast path first

For one-off or short workloads, construct BinaryFFTPlan(n, method="codelet8") and call plan.execute(x), optionally with out= for a caller-owned output buffer. This path performs no calibration. Inputs must be contiguous one-dimensional NumPy uint8 or bool arrays containing only zero and one. Outputs are complex128; new outputs are independent by default.

For heavy repeated use, get_plan(n, dtype) or binary_fft(x) opts into cached autotuning. The first call is expensive. Up to eight plans are cached in process by size and dtype. Repeated execution does not retune; plan.retune() is explicit. The README contains complete runnable examples and close/clear-cache behavior.

Choice penalty compares the same candidate kernels on held-out timing samples, independently of noisy selected-call timing. Autotuning requires at least an 8% lookup advantage and lookup wins in at least 75% of calibration rounds; otherwise it chooses arithmetic. This deliberately rejects marginal wins, but it cannot guarantee the fastest method on future inputs or under changing machine load.

Calibration is worth paying only with enough reuse

Measured default calibration cost was roughly 0.44 to 0.81 seconds through N = 262,144, and 4.02 seconds at N = 1,048,576. At N = 4,096 the observed saving versus fixed arithmetic8 took about 317,000 transforms to repay calibration. At N = 65,536 the selector chose arithmetic8, so there is no demonstrated payback over choosing that kernel directly. Use fixed mode unless the expected repeated workload justifies tuning.

Held-out tests used eight new seeds per size and 13 randomized timing rounds, separate from calibration. All results matched NumPy; worst absolute error was 2.28e-12. Repeated calls kept calibration_count at one, cached plans were reused, and invalid input, output alignment, aliasing, closed-plan and buffer-ownership checks passed. Public API timing includes validation, ctypes dispatch and optional output allocation; raw sample overlap prevents a reliable isolated dispatch-overhead claim.

Selective FFT caching benchmark

Measured on 8 October 2026 | Random binary inputs | Single cloud CPU

A fixed lookup table for small binary FFT leaves reduces bookkeeping and clearly improves the Python prototype. In compiled C, the benefit is size dependent and shrinks against a good arithmetic leaf kernel. At the original size of 65,536, an 8-bit table does not establish a dependable improvement over the best arithmetic implementation. A 16-bit table is consistently unattractive at larger sizes.

The arithmetic controls include fused 4, 8 and 16 point real-input codelets; this avoids attributing a win merely to removing recursion or combining small stages.

What the timing includes

The C timing includes input permutation and gathers, packing each binary key, copying its full output row, and every remaining FFT merge. It excludes input generation, output allocation and reusable table or plan creation. The original input is never assumed to arrive already bit-packed or already permuted.

Each native sample cycles through 16 distinct seeded inputs. Methods run in randomized order on one pinned CPU. The initial experiment used 11 samples of about 40 ms; confirmation used 21 samples of about 100 ms. Shared virtualized hardware still introduces noise, so differences of a few percent should not determine a production choice without a target-machine test.

C entries contain full complex128 spectra, 16 bytes per complex output. Python stores object tuples and complex objects: about 3.3 KiB, 92 KiB and 43 MiB for 4, 8 and 16 bit leaves. C setup is allocation plus population, measured 11 times; the first construction is also shown. These are setup costs, not controlled cold-cache latency measurements.

An 8-bit table needs only 256 entries. A 16-bit table needs 65,536 entries and adds random memory traffic; fewer arithmetic operations do not guarantee less time. To amortize a table, the number of transforms must exceed table setup time divided by the positive per-transform saving. If the warm variant loses, repeated use cannot amortize that loss.

Recommended implementation

Start with a fixed 8-bit direct-index table, and also benchmark 4-bit and arithmetic codelet leaves. Pack the actual decimated FFT leaf into an integer key and index a flat read-only array. No hash table, canonical node IDs, LRU policy or per-node allocation is needed.

Above the cutoff, run the ordinary FFT with no duplicate tracking. Reuse twiddles, input permutation and working buffers across calls. Select the best leaf method once per size and precision, rather than maintaining adaptive bookkeeping inside every FFT.

For uniform random input, avoid caching large subproblems. At N = 65,536 the expected repeated fraction is about 96.875% for 8-bit subproblems, 3.06% for 16-bit subproblems and 0.000024% for 32-bit subproblems. A partial table of equally likely random patterns has no privileged frequent subset.

An untested next candidate is a packed 8-bit real-input table. Store DC and Nyquist as real numbers plus three complex bins: eight doubles, 64 bytes per pattern, 16 KiB total. Reconstruct conjugate bins while writing the full output. Its extra reconstruction work needs measurement; no speedup is claimed here.

Correctness and limits

The C variants passed 630 complete FFT tests through N = 1,048,576, five random seeds per tested size and structured inputs, plus every 4, 8 and 16 bit table row. Worst complete-transform absolute error versus NumPy was 2.24e-12. Python tests covered three seeds and sizes for all eight methods, exhaustive 4 and 8 bit rows, and structured inputs; worst error was 4.34e-13. ASan and UBSan checks passed; leak detection was unavailable under sandbox tracing.

The algorithm is still O(N log N) for a fixed small cutoff. An 8-bit table eliminates three merge levels from online execution; it does not establish a new asymptotic FFT bound or a general-purpose speed advantage. Native code is a purpose-built binary-input microbenchmark, not a replacement claim for FFTW or other tuned libraries.

SciPy and NumPy practical comparisons are retained in the JSON. Their calls include Python dispatch and output allocation, unlike the preallocated C kernel. SciPy rfft returns only N/2 + 1 bins, so its result is contextual and is not an equivalent full-output comparison. All use the same numerical precision.

Reproduce the experiment

The accompanying ZIP contains C source and an auto-compiling Python harness, the Python lookup experiment, the unchanged earlier prototype, and both native datasets. Requirements: Python 3, NumPy, SciPy and GCC on a POSIX platform. No installation or network access is performed by the scripts. Run commands are in README.md.

Environment: AMD EPYC 9V74, Linux x86-64 cloud VM; GCC 14.2.0 with -O3 -march=native, double precision; NumPy 2.3.5 and SciPy 1.17.0. Results apply to this implementation and machine.

Sources: the supplied fft_collision_research.py and fft_collision_research_notes.md; FFTW documentation on generated small codelets (https://fftw.org/fftw3_doc/Generating-your-own-code.html) and reusing plans (https://www.fftw.org/faq/section3.html). The binary lookup design and measurements here are an experiment, with no claim of novelty.
